## 0. 결론 먼저

○ **실측에서 밟은 지뢰 세 개를 코드가 막도록 했습니다.**
  task 유실 · 내장 GPU 커널 컴파일 · 예열 부족 — 셋 다 「조용히 틀리거나
  느려지는」 종류라 사람 눈으로는 안 잡힙니다

○ **예열 횟수를 실측해서 정했습니다.** OpenVINO 는 **17회째**에 안정됩니다.
  전에 쓰던 3회로는 전혀 부족했습니다 — 예열 3회 뒤 첫 추론이 **609ms**
  (안정값의 11배)였습니다. **20회**로 잡았습니다

○ **ONNX·OpenVINO 산출물이 모델 목록에 뜹니다.** 도메인·백엔드는 원본
  `.pt` 에서 물려받고, **「운영에 적용되어 있지 않습니다」**가 설명에 붙습니다

○ **연결한 곳은 시험 탐지(S-61) 경로뿐입니다.** 상시 탐지는 워처 재구성이
  얽혀 있어 별도 작업입니다

○ 회귀 **1,009건 통과 · 3건 건너뜀 · 실패 0** (272초)

## 1. 신설 — `core/inference.py` (172줄)

런타임 관련 결정을 **한곳에 모았습니다.** 흩어져 있으면 부르는 쪽마다
빠뜨립니다 — 실제로 기존 `YOLO()` 호출 **6곳 중 어느 곳도 task·device 를
넘기지 않고** 있었습니다.

### 막아 주는 것 세 가지

| # | 함정 | 대책 |
|---|---|---|
| 1 | **task 유실** — 분할 모델이 검출로 열려 마스크 계수 32개를 클래스 점수로 읽음 | `load()` 가 **task 를 필수 인자로** 받고, 열린 뒤 실제 task 를 **대조**해 다르면 예외 |
| 2 | **내장 GPU 커널 컴파일** — 한 회차가 499초까지 늘어진 사례 | `predict()` 가 **장치를 CPU 로 고정** |
| 3 | **예열 부족** | 런타임별 횟수로 자동 예열 |

**기본값을 두지 않았습니다.** `task` 에 기본값이 있으면 부르는 쪽이 안
넘기게 되고, 그 순간 1번 함정이 되살아납니다. **거부가 잘못된 결과보다
낫습니다.**

### 예열 횟수 — 추측이 아니라 측정

640×640 빈 프레임으로 40회 연속 추론하며 언제 안정되는지 쟀습니다
(2026-08-17, i7-1360P).

| 런타임 | 1회차 | 안정화 시점 | 안정값 |
|---|---|---|---|
| **OpenVINO** | 7,441ms | **17회째** | 54ms |
| **ONNX** | 1,024ms | **2회째** | 190~250ms |

```
OpenVINO  7441 694 916 889 463 927 1029 898 834 816 785 982
          1151 950 831 436 | 61 48 51 50 54 54 54 53 ...
                            └─ 17회째부터 고정
```

**적용 결과** — 로드 직후 첫 추론이 바로 안정값으로 나옵니다.

| 런타임 | 로드+예열 | 예열 직후 5회 |
|---|---|---|
| OpenVINO | 26.7초 | 53 · 51 · 51 · 50 · 57ms |
| ONNX | 1.5초 | 167 · 195 · 216 · 257 · 233ms |
| PyTorch | 2.0초 | 451 · 486 · 476 · 455 · 464ms |

> ⚠️ **OpenVINO 는 기동에 약 27초가 듭니다.** 상시 탐지에 적용하면 서비스
> 기동이 그만큼 늦어집니다. 그 대가로 **첫 실탐지부터 제 속도**가 납니다.
> 39지점에 각각 예열하면 합이 커지므로, 적용 시 **모델 인스턴스 공유**를
> 함께 검토해야 합니다.

## 2. 확장 — `core/model_registry.py`

`.pt` 만 훑고 있어 변환 산출물이 **목록에서 보이지 않았습니다.** 안 보이면
화면에서 비교할 수가 없습니다.

| 항목 | 처리 |
|---|---|
| 탐색 위치 | `models/candidates/` — 학습 결과 전체를 훑으면 목록이 두 배가 됨 |
| 인식 | `.onnx` 파일 · `*_openvino_model` 폴더 |
| **도메인·백엔드** | **원본 `.pt` 에서 물려받음** |
| 라벨 | 「… — ONNX Runtime」처럼 런타임을 드러냄 |
| 설명 | **「운영에 적용되어 있지 않습니다」** + 실측 배수 |
| `in_use` | **비움** — 운영 표시를 절대 달지 않음 |

**도메인·백엔드를 물려받는 것이 핵심입니다.** 파일명만 보고 추측하면
`best.onnx` 가 분할인지 검출인지 알 수 없고, 그것을 틀리면 1번 함정입니다.

### 확인된 결과

```
models/candidates/best.onnx              [flood/yolo-seg → task=segment]
models/candidates/best_openvino_model    [flood/yolo-seg → task=segment]
models/candidates/yolo11s.onnx           [crowd/yolo-det → task=detect]
models/candidates/yolo11s_openvino_model [crowd/yolo-det → task=detect]
```

`best.onnx` 가 **segment 로 풀립니다** — 실측 때 무너졌던 바로 그 지점입니다.

## 3. 연결 — `core/model_probe.py` (시험 탐지 경로만)

`YOLO(...)` 직접 호출 3곳을 공통 로더(`_open()`)로 바꿨습니다.

| 위치 | 용도 |
|---|---|
| `_annotate_road` | 노면 미리보기 |
| `_probe_crowd` | 인파 계수 |
| `_probe_flood` | 수면 비율 (YOLO 백엔드) |

**예열은 하지 않습니다.** 시험은 프레임 몇 장이라 예열이 추론보다 오래
걸립니다(OpenVINO 약 27초). 여기서 중요한 것은 속도가 아니라 **결과가
맞는가**입니다.

> 시험 탐지는 「이 모델이 쓸 만한가」를 판단하는 자리입니다. task 가 틀린
> 상태로 나온 결과를 보면 **멀쩡한 모델을 버리게 됩니다.**

## 4. 시험 — `tests/core/test_inference_runtime.py` (14건)

### 전체 회귀 결과

| 구분 | 결과 |
|---|---|
| 신규 시험 | **14건** (모두 통과) |
| 전체 회귀 | **1,009건 통과 · 3건 건너뜀 · 실패 0** |
| 소요 | **272초 (4분 32초)** — 기준선(297초)과 같은 수준 |

직전 기준선이 995건이었으므로 **995 + 14 = 1,009** 로 맞습니다. 변환 산출물이
있어 건너뛰기로 표시한 2건도 실제로 돌았습니다 — **결과 동일성 시험이
실행되어 통과**했다는 뜻입니다.


실측에서 밟은 지뢰를 그대로 못박았습니다.

| 시험 | 지키는 것 |
|---|---|
| `task를_비우면_거부한다` | 기본값을 두지 않는다 |
| `분할_모델은_분할로_열린다` | 1번 함정 재발 방지 |
| `변환_전후_검출_결과가_같다` | **IoU 로 짝지어** 비교 |
| `예열_횟수는_런타임마다_다르다` | OpenVINO ≥ 17회 |
| `변환_후보는_운영으로_표시되지_않는다` | 운영/후보 혼동 방지 |
| `운영_기본값은_변환_후보로_바뀌지_않는다` | 기본 선택이 흔들리지 않음 |
| `변환_후보는_원본에서_도메인과_백엔드를_물려받는다` | 추측 금지 |

**비교는 IoU 로 합니다.** 신뢰도 내림차순으로 자리끼리 맞대면, 신뢰도가
같은 상자의 순서가 뒤집혀 **좌표가 590px 달라 보입니다**(실측 때 실제로
그랬고, 실제로는 같은 상자였습니다).

변환 산출물은 저장소에 커밋하지 않으므로(수십 MB), 없으면 해당 시험은
**건너뜁니다.**

## 5-1. ⚠️ 첫 회귀가 무효였던 일 — 기록해 둡니다

처음 돌린 회귀는 **13 실패 · 467 건너뜀 · 4,309초(1시간 12분)** 였습니다.
숫자만 보면 이번 변경이 무언가를 깨뜨린 것처럼 보였습니다.

**원인은 PostgreSQL 이 내려가 있던 것이었습니다.**

| 증상 | 실제 원인 |
|---|---|
| 467건 건너뜀 (기준 3건) | DB 의존 시험이 전부 skip |
| 13건 실패 (노면·상시탐지) | DB 가 필요한 시험 |
| 4,309초 (기준 297초) | 접속 재시도 대기 |

DB 를 5433 으로 올린 뒤 **실패했던 13건을 그대로 다시 돌리니 51건 전부
통과(27.8초)** 했습니다.

> **지난번 「53분 회귀」와 같은 종류의 함정입니다.** 그때는 라이브 서비스의
> 스트림 재접속이 원인이었고 이번엔 DB 정지인데, 공통점은
> **「측정 환경이 정상인지 먼저 확인하지 않은 것」** 입니다.
> **전체 회귀 전에 DB 기동 여부를 먼저 봅니다.**
>
> 참고 — `pg_ctl start` 만으로는 5432 에 붙습니다. **`-o "-p 5433"`** 를
> 반드시 넘겨야 합니다.

## 7. ⚠️ 여전히 사실인 것

**ONNX·OpenVINO 로 바꿔도 AGPL 은 해소되지 않습니다.** 런타임만 바뀔 뿐
가중치와 학습 코드의 라이선스는 그대로입니다. 라이선스는 **모델을 갈아야**
풀리며, 그것은 계획 B(보류 중)의 몫입니다.
