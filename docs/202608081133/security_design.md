## 1. 보안 목표와 위협

### 1-1. 이 시스템이 다루는 것

| 자산 | 민감도 | 위협 |
|---|---|---|
| **CCTV 실시간 영상** | 높음 | 시민 얼굴·차량번호 노출, 무단 열람 |
| **주민 경보 발송 권한** | **매우 높음** | 오발송 시 사회적 혼란, 기관 신뢰 훼손 |
| **시설물 제어 권한** | **매우 높음** | 차단기 오작동 시 인명 위험 |
| 운영 계정 | 높음 | 계정 탈취 → 위 두 권한 획득 |
| 이벤트·조치 이력 | 중간 | 사후 책임 규명 자료. 변조 시 감사 불가 |
| 현장 제보 사진 | 높음 | 개인정보 포함 가능 |

### 1-2. 가장 큰 위협은 「권한 없는 발송·제어」입니다

영상 유출보다 **오발송과 오작동의 피해가 더 큽니다.** 주민 경보는 되돌릴 수
없고, 차단기 오작동은 사람이 다칠 수 있습니다. 그래서 이 두 가지에 가장 강한
통제를 걸었습니다(4절).

### 1-3. 실제로 있었던 사고

> **알림 발송 API에 인증이 없었습니다.** 엔드포인트마다 권한 의존성을 붙이는
> 방식이었고, **하나를 빠뜨린 것을 아무도 몰랐습니다.**

이 사고가 2절의 「기본 거부」 구조를 낳았습니다.

## 2. 인증·인가 구조 ★

### 2-1. 전역 가드 — 기본 거부 (fail-closed)

모든 요청이 `AuthGuard` 미들웨어를 지납니다. **경로 규칙표에 없는 `/api` 경로는
403입니다.**

```
요청 → [공개 경로?] → [세션 검증] → [임시 비밀번호?] → [규칙표 조회] → [권한 판정] → 실행
                          ↓ 실패          ↓ 예            ↓ 없음(/api)      ↓ 실패
                       401/303       비밀번호 변경        **403**          403
```

**엔드포인트마다 붙이지 않고 한곳에서 판정합니다.** 새 API를 만들면서 규칙
등록을 잊으면 **동작하지 않으므로**, 보안이 빠진 채 조용히 열려 있는 상태가
생기지 않습니다.

| 공개 경로 (인증 불필요) | 사유 |
|---|---|
| `/login`, `/logout` | 로그인 절차 |
| `/static/`, `/favicon.ico` | 정적 자원 |
| `/api/health` | 로드밸런서·감시용 |

> **최소한으로 유지합니다.** 목록을 늘릴 때는 노출되는 정보를 반드시 검토하세요.
> `/api/health` 는 지점 수·소스 모드를 노출하므로, 외부 공개망에 두면 안 됩니다.

### 2-2. 세션

| 항목 | 값 | 비고 |
|---|---|---|
| 방식 | itsdangerous 서명 쿠키 | 서버 세션 저장소 불필요 |
| 쿠키명 | `urbanguard_session` | |
| **HttpOnly** | ✅ 적용 | JS 접근 차단 (XSS 시 탈취 방지) |
| **SameSite** | ✅ `lax` | CSRF 완화 |
| **Secure** | ⚠️ **환경변수로 제어** | `URBANGUARD_COOKIE_SECURE=1` — **배포 시 필수** |
| 유효기간 | 8시간 | `URBANGUARD_SESSION_MAX_AGE` |
| 페이로드 | `{uid, lid, role}` | 비밀번호·개인정보 미포함 |

> **⚠️ 서명 키(`URBANGUARD_SECRET_KEY`)를 지정하지 않으면 프로세스마다 새 키가
> 생성됩니다.** 재시작할 때마다 전원 로그아웃되며, 개발 편의용 동작입니다.
> **운영 배포 시 반드시 고정 키를 발급하고 형상관리에서 제외**하세요.

### 2-3. 비밀번호

| 항목 | 값 | 근거 |
|---|---|---|
| 해시 | **bcrypt** (직접 사용) | passlib 의존 회피 |
| 최소 길이 | 9자 | `URBANGUARD_MIN_PASSWORD_LEN` |
| 조합 | 영문 대/소문자·숫자·특수문자 중 **3종 이상** | |
| 로그인 실패 잠금 | **5회 → 10분** | `URBANGUARD_MAX_FAILED_LOGIN` / `LOCK_MINUTES` |
| 최초 발급 | 임시 비밀번호 자동 생성 | |
| **강제 변경** | ✅ 임시 비밀번호 상태에서는 **다른 화면 접근 불가** | |

임시 비밀번호 상태의 계정은 비밀번호 변경 화면과 로그아웃 외 어디로도 갈 수
없습니다. 다만 **이 두 경로까지 막으면 비밀번호를 바꿀 수도 없는 상태**가 되므로
예외로 열어 두었습니다.

**기준을 모두 환경변수로 뺐습니다** — 기관 보안지침이 다르면 코드 수정 없이
맞출 수 있습니다.

## 3. 권한 매트릭스

### 3-1. 역할

| 역할 | 대상 부서 | 범위 |
|---|---|---|
| `SYS` 시스템관리자 | 정보통신 | 전 기능 |
| `MGR` 부서담당자 | 안전총괄·도로 | **담당 도메인만** |
| `OPR` 관제요원 | 상황실 | 전 도메인 관제·탐지 실행. 설정 불가 |

### 3-2. ★ 도메인 범위 검사는 MGR에만 적용합니다

관제요원은 상황실에서 **세 도메인을 모두 봐야 합니다.** 도메인으로 가르면
야간 1인 근무 시 아무것도 못 보는 상황이 생깁니다.

부서담당자는 반대로 **자기 부서 소관만** 보는 것이 맞습니다. 도로관리과
담당자가 인파 통제 이력을 볼 이유가 없습니다.

### 3-3. 자원 × 행위

15개 자원 × 4행위(`view`/`edit`/`execute`/`request`)로 판정합니다.

| 자원 | SYS | MGR | OPR |
|---|---|---|---|
| `dashboard` 상황판 | 전체 | 담당 | 전체 |
| `event` 이벤트 | 전체 | 담당 | 전체 |
| `monitor` 관제 | 전체 | 담당 | 전체 |
| `detect` 탐지 실행 | ✅ | ✅ 담당 | ✅ |
| `notify` 알림 | 발송 | 발송 | **요청만** |
| `notify_agency` 기관 통보 | ✅ | ✅ | ❌ |
| `facility` 시설물 제어 | ✅ | ✅ | 요청 |
| `facility_mode` 제어 모드 변경 | ✅ **전용** | ❌ | ❌ |
| `settings_ops` 운영 설정 | ✅ | ✅ 담당 | ❌ |
| `settings_sys` 시스템 설정 | ✅ | ❌ | ❌ |
| `users` 계정 관리 | ✅ | ❌ | ❌ |
| `audit` 감사 로그 | 전체 | **본인 부서** | ❌ |

**관제요원이 직접 발송할 수 없는 것이 핵심입니다.** 야간에 혼자 있는 사람이
주민 경보를 단독으로 내보내는 상황을 구조적으로 막습니다.

## 4. 고위험 기능의 이중 통제 ★

### 4-1. 주민 경보 — 2인 승인

```
 [요청]  누구든 요청 가능 (OPR 포함)
    ↓
 [승인]  요청자와 **다른 사람**이 승인해야 발송
    ↓
 [발송]  notifications 에 요청자·승인자 모두 기록
```

> **⚠️ 자가 승인 금지는 역할과 무관합니다.** 초기 구현에서 부서담당자가 자기
> 요청을 스스로 승인할 수 있는 구멍이 있었고, **역할이 아니라 사람 기준**으로
> 판정하도록 고쳤습니다.

**예외 — 「심각」 단계 단독 발송**
급박한 상황에서 승인자를 기다릴 수 없는 경우를 위해 단독 발송을 허용하되,
**사후 승인 대상**으로 표시하고 감사 로그에 `notify.solo_send` 로 남깁니다.

### 4-2. 시설물 제어 — 3단계 모드

| 모드 | 동작 | 기본값 |
|---|---|---|
| **권고만** | 화면에 「무엇을 해야 하는지」만 표시. 제어 안 함 | ✅ **기본** |
| 원격요청 | 담당자 확인 후 제어 명령 전송 | |
| 자동 | 조건 충족 시 자동 제어 | |

**기본값이 「권고만」인 이유** — 차단기·경보기 오작동은 사람이 다칠 수 있습니다.
검증되지 않은 상태에서 자동 제어를 켜 두는 것은 위험합니다.

**모드 변경은 시스템관리자 전용**(`facility_mode`)입니다. 관제요원·부서담당자는
바꿀 수 없습니다.

## 5. 감사 추적

### 5-1. 기록 대상

| 분류 | 액션 |
|---|---|
| 인증 | `login.success` / `login.failure` / `login.locked` / `logout` |
| 계정 | `user.create` / `user.update` / `user.deactivate` / `user.password_reset` |
| **알림** | `notify.request` / `notify.approve` / `notify.reject` / `notify.send` / **`notify.solo_send`** |
| 설정 | `settings.update` |
| 탐지 | `detect.run` |
| 보고서 | `report.export` |

### 5-2. 변경 전후를 남깁니다

`audit_logs` 에 `before` / `after` 를 JSON으로 기록해, **무엇이 어떻게 바뀌었는지**
사후에 확인할 수 있습니다. 접속 IP도 함께 남기며, 리버스 프록시 뒤에서는
`X-Forwarded-For` 를 우선합니다.

### 5-3. ★ 계정을 지워도 감사 기록은 남습니다

`audit_logs.user_id` 는 `SET NULL` 이고, **`login_id` 와 `dept` 를 문자열로 복제**해
둡니다. 계정이 삭제돼도 「누가 했는지」가 남습니다.

### 5-4. ⚠️ 한계

- **감사 로그 자체의 변조 방지 장치가 없습니다.** DB 관리 권한이 있으면 수정
  가능합니다. 요건이라면 별도 저장소로의 전송(WORM/로그 서버)이 필요합니다.
- **조회 이력은 남기지 않습니다.** 누가 어떤 CCTV를 봤는지는 기록되지 않으며,
  영상 열람 이력이 요건이면 추가 개발이 필요합니다.

## 6. ⚠️ 운영 전 필수 조치

**아래는 현재 적용되지 않은 것들입니다.** 시범운영 전에 처리해야 합니다.

| # | 항목 | 현재 | 위험 | 조치 |
|---|---|---|---|---|
| **1** | **HTTPS** | ❌ HTTP | **세션 쿠키·비밀번호가 평문으로 전송** | nginx 등 리버스 프록시에서 TLS 종단 |
| **2** | **`URBANGUARD_COOKIE_SECURE=1`** | ❌ 미설정 | 쿠키가 평문 경로로 전송 | HTTPS 적용과 동시에 설정 |
| **3** | **운영 서명 키 발급** | ⚠️ 개발 키 | 세션 위조 가능 | 신규 키 발급, 형상관리 제외 |
| 4 | DB 계정 분리 | ❌ 단일 계정 | 앱 침해 시 스키마 변경까지 가능 | 앱용 계정에 DDL 권한 제거 |
| 5 | 저장 데이터 암호화 | ❌ 미적용 | DB 파일 유출 시 전량 노출 | **법적 의무 대상 여부 확인 필요** |
| 6 | 정기 백업 자동화 | ❌ 수동 | 장애 시 복구 불가 | `pg_dump` 스케줄링 |
| 7 | 로그 수집 | ⚠️ `print()` 잔존 | 사고 시 추적 곤란 | `logging` 전환 후 파일 수집 |
| 8 | 접속 IP 제한 | ❌ 없음 | 관제망 외부 접근 | 방화벽 또는 앱 레벨 허용 목록 |
| 9 | 세션 강제 종료 | ❌ 없음 | 퇴직자 세션이 8시간 유효 | `sessions` 테이블 도입 |
| 10 | 비밀번호 재사용 금지 | ❌ 없음 | 같은 비밀번호 반복 | `password_history` 도입 |

**1·2·3번이 최우선입니다.** 셋 다 코드 변경 없이 배포 설정만으로 해결됩니다.

## 7. 적용된 방어

| 위협 | 대응 | 상태 |
|---|---|---|
| SQL 인젝션 | SQLAlchemy ORM 파라미터 바인딩 | ✅ |
| XSS | Jinja2 자동 이스케이프 | ✅ |
| 세션 탈취(XSS) | HttpOnly 쿠키 | ✅ |
| CSRF | SameSite=lax | ⚠️ **토큰 미적용** (7-1절) |
| 무차별 대입 | 5회 실패 시 10분 잠금 | ✅ |
| 권한 상승 | 전역 가드 + 기본 거부 | ✅ |
| 미인증 API 노출 | 규칙 미등록 시 403 | ✅ |
| 오발송 | 2인 승인 | ✅ |
| 오작동 | 제어 모드 기본 「권고만」 | ✅ |
| 개인정보 노출 | 사람 영역 픽셀화 | ✅ (8절) |
| 경로 조작 | 미디어 경로 검증 | ✅ |

### 7-1. ⚠️ CSRF 토큰이 없습니다

`SameSite=lax` 로 완화돼 있으나 **전용 토큰은 적용하지 않았습니다.**
lax 는 폼 POST를 다른 사이트에서 보내는 것을 막지만, 브라우저 구현과 설정에
의존합니다.

**설정 변경·알림 요청 등 상태를 바꾸는 POST가 다수 있으므로**, 기관 보안지침이
CSRF 토큰을 요구한다면 추가 개발이 필요합니다.

| **실패 시 미표시** | 가리지 못하면 화면에 내보내지 않고 상태만 알립니다 |
| **최소 수집** | 주민등록번호·계좌번호 등은 수집하지 않습니다 |

### ⚠️ 한계

- **차량번호판은 자동으로 가리지 못합니다.** 전용 모델이 없어 담당자 육안
  확인에 의존하며, 이 사실을 화면에 표시합니다.
- **실시간 관제 화면의 CCTV 영상 자체는 마스킹하지 않습니다.** 관제 목적상
  사람을 봐야 하기 때문이며, 저장·공유되는 스냅샷만 가립니다.
