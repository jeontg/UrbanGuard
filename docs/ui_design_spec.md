> 국내외 안전 기준은 전부 **물리 단위**(침수심 cm · 명/㎡ · 구간 단위 지수)인데

> 기준이 있어도 연결할 수 없었고, 그래서 「기준에 따라 판정한다」고 말할 수
> 없었습니다. 보정이 그 한 칸을 메웁니다(`threshold_rationale.md`).

#### S-92 오류 관리 — 화면 구성

| 영역 | 내용 |
|---|---|
| ① 요약 카드 | 미처리 **심각** · 미처리 전체 · 총 발생 횟수 · 가장 많이 난 오류 5종 |
| ② 검색 | 검색어 · 분류 · 심각도 · 발생위치 · 처리여부 · 기간 |
| ③ 목록 | 최근 발생 · 코드 · 심각도 · 오류명/메시지 · 위치 · **횟수** · 상태 |
| ④ 펼침 | **원인 · 해결방법**(사전에서) · 전체 메시지 · 상세 · 조치 입력 |
| ⑤ 일괄 정리 | 「처리완료 건 중 N일 이전」 삭제 |

**같은 오류는 한 줄로 묶고 횟수만 올립니다.** CCTV 재접속 실패는 초당 수십 번
나므로, 발생마다 한 줄이면 중요한 오류가 그 속에 묻힙니다.

#### S-93 오류 코드 사전 — 화면 구성

| 영역 | 내용 |
|---|---|
| ① 등록·수정 폼 | 코드 · 분류 · 심각도 · 사용여부 · 오류명 · 원인 · 해결방법 |
| ② 검색 | 검색어 · 분류 |
| ③ 목록 | 코드 · 분류 · 심각도 · 오류명(펼침) · **최근 30일 발생** · 구분 · 관리 |

기본 제공 코드(28종)는 **삭제할 수 없습니다** — 지워도 그 코드로 오류는 계속
쌓이고 설명만 사라집니다. 「사용 안 함」으로 감춥니다.

#### S-61 확장 — 세 부분

| 영역 | 내용 |
|---|---|
| ① 운영 모델 지정 | 도메인별 모델 선택 + **반영 시점 안내** + 비고 편집 |
| ② 모델 시험 탐지 | 모델 × 지점 × 관측시간 × 임계값 → 실행 → 지표 + **미리보기 화면** |
| ③ 모델 현황 표 | 상태(계산값) · 실제 파일 · 탐지·오탐 실적 · 비고(운영자 판단) |

> **시험은 운영을 건드리지 않습니다.** 결과는 이벤트·노면 현황에 남지 않고,
> 시험대에서 고른 모델이 상시 탐지에 반영되지도 않습니다. 화면에 그렇게 적어
> 두었습니다 — 안 적으면 바뀐 줄 압니다.

> **반영 시점이 도메인마다 다릅니다.** 노면은 즉시, 침수·인파는 재기동 필요.
> 이 차이를 감추면 바뀐 줄 알고 관제하게 됩니다.

## 3. 설계 원칙

| 원칙 | 내용 | 이유 |
|---|---|---|
| **이벤트 중심** | 도메인이 아니라 「사건」이 1급 단위 | 관제요원은 도메인별로 근무하지 않는다 |
| **한 호흡 완결** | 발견→확인→통보→기록을 한 화면에서 | 화면 이동이 골든타임을 깎는다 |
| **지표 최소주의** | 상태 스트립은 5개까지 | 지표가 늘수록 반응시간이 느려진다 |
| **설정의 화면화** | 설정파일 직접 편집을 전부 화면으로 | 지자체 담당자가 파일을 편집할 수 없다 |
| **모든 조치는 기록** | 통보·제어·설정변경은 감사로그 필수 | 공공기관 감사 대응 |
| **접근성 내장** | 설계 단계부터 반영 | 사후 적용은 전면 재작업 |
| **기관 비종속** | 기관명·지점·임계값은 전부 설정값 | 부울경 타 지자체 확장 |
| **안전측 기본값** | 제어는 「권고」, 알림은 「승인 필요」가 기본 | 되돌릴 수 없는 행위를 기본값으로 두지 않는다 |

### 6-3. 판단 근거가 필요한 두 가지

**① 왜 기관 통보는 관제요원 단독인가**
관제 운영 규정상 관제요원은 범죄·사고·재난 발견 시 **즉시** 112상황실·재난상황실에 통보하게 되어 있습니다. 여기에 승인 절차를 넣으면 규정과 충돌합니다.

**② 왜 제어 모드 변경은 SYS 전용인가**
자동 제어 전환은 **시스템의 책임 범위를 바꾸는 행위**입니다. 현장 판단으로 켜고 끌 수 있으면 안 됩니다.

### 6-4. DB 스키마로의 귀결

> ### ⚠️ 이 절의 스키마는 **설계 단계의 스케치**였습니다
> **실제 구현된 스키마와 다릅니다.** 정확한 명세는
> **`docs/202608131503/db_design_spec.md`(데이터베이스 설계서 v4)** 를 보십시오.
> 그 문서는 운영 중인 DB에서 직접 읽어 작성했습니다.
>
> 주요 차이
> - 스케치에 없던 **`cameras` · `camera_domains` · `camera_rois`** 3개 테이블이 실제로 존재합니다
> - `citizen_reports` · `app_settings` 도 추가됐습니다
> - `shift_handovers` 는 **아직 만들지 않았습니다**(S-04 미구현)
> - `notifications.event_id` 는 실제로는 `case_id`(문자열)입니다
>
> 아래는 설계 의도를 남기기 위한 기록으로만 보십시오.

```
users            (id, login_id, name, dept, role, is_active,
                  pw_hash, pw_updated_at, failed_count, locked_until, last_login_at)
user_domains     (user_id, domain)                    ← MGR 담당 도메인
events           (id, domain, block_id, type, level, status,
                  detected_at, closed_at, assignee_id, confidence)
event_actions    (id, event_id, user_id, action, memo, created_at)
notifications    (id, event_id, tier, channel, status, body, recipients_count,
                  requested_by, approved_by, requested_at, approved_at, sent_at,
                  needs_post_approval)                ← 2인 승인이 컬럼으로
facility_controls(id, facility_id, mode, command, result, requested_by, created_at)
shift_handovers  (id, from_user_id, to_user_id, note, event_ids, created_at)
audit_logs       (id, user_id, login_id, dept, action, target, before, after, ip, created_at)
```

**events / event_actions 가 v4의 핵심 추가분**입니다. 이벤트가 1급 단위가 되면서 모든 화면이 이 위에 올라갑니다.

### 6-5. 탐지 대상 관리 구조 (v4.2 추가)

세 탐지서비스가 **같은 CCTV를 공유**하되 각자 다른 영역을 보고, 각자 켜고 끌 수
있어야 합니다. 이를 3계층으로 나눴습니다.

| 계층 | 저장 | 화면 | 의미 |
|---|---|---|---|
| ① 지점 | `cameras` | S-80 등록 | CCTV가 존재한다 |
| ② 서비스 지정 | `camera_domains.enabled` | S-80 탐지 지정 | 이 서비스가 이 지점을 쓴다 |
| ③ 상시 탐지 | `camera_domains.continuous` | S-80 탐지 지정 | 요청 없이도 계속 본다 |
| ④ 관심영역 | `camera_rois` | S-81 | 영상의 어느 부분을 보는가 |

**②만 켜고 ③을 끄면 「선택 탐지」**입니다 — 관제요원이 화면에서 지점을 골라
실행할 때만 분석합니다.

### ★ S-01 통합 상황판

#### 설계 원칙 — 「많은 정보」와 「최소주의」를 정보 위계로 화해시킵니다

상황판에 정보를 많이 담자는 요구와, COP는 최소로 유지하라는 원칙은 정면으로 부딪힙니다.
**둘 다 맞습니다.** 해법은 정보를 줄이는 것이 아니라 **읽는 시간대별로 층을 나누는 것**입니다.

| 층 | 읽는 시간 | 무엇 | 위치 |
|---|---|---|---|
| **1층** | **3초** — 지금 비상인가 | 재난단계·미처리 건수·강수·조위·시스템 상태 | 상단 상태바 (항상) |
| **2층** | **30초** — 어디서 무슨 일인가 | 지도 · 이벤트 큐 | 주 영역 (항상) |
| **3층** | **3분** — 조사·판단 | 이벤트 상세 · CCTV 그리드 · 타임라인 · 오늘 현황 | 하단 전환 패널 (탭) |
| **참조** | 필요할 때 | 기상·수문·조위 상세, 통보 이력, 당직 | 우측 접이식 패널 |

**1층은 여전히 최소입니다.** 정보량이 늘어난 곳은 3층과 참조층이고, 이 둘은
**평상시 시선을 뺏지 않습니다.** 최소주의 원칙은 「화면 전체」가 아니라
「항상 보이는 영역」에 적용됩니다.

**조위를 넣은 이유**: 부산은 해안도시라 **만조와 호우가 겹치면 배수가 안 됩니다.**
초량·범내골 같은 저지대는 강수량만으로 위험을 판단할 수 없습니다. 강수·하천·조위를
함께 봐야 하며, 이건 부산 지역 솔루션의 차별점이기도 합니다.
⚠️ 조위 데이터 출처(국립해양조사원 등) 확인이 필요합니다.

#### ⑤ 하단 전환 패널 — 4개 탭

| 탭 | 내용 | 근거 |
|---|---|---|
| **이벤트 상세** | 선택 이벤트의 근거·조치 버튼 | 기본 탭 |
| **CCTV 그리드** | 감시 지점 썸네일 일괄 표출, 등급별 테두리 색 | 관제의 기본. 지점이 늘수록 필수 |
| **위험도 타임라인** | 지점 × 시간 히트맵 | **기존 flood3 자산에 이미 있음** — 재활용 |
| **오늘 현황** | 탐지·처리 건수, 평균 대응시간, 통보 건수 | 교대 인수인계·성과 집계의 원천 |

#### ④ 환경 패널 (우측 접이식)

강수 실황·예보, 조위·만조 시각, 하천 수위. **접었다 펼 수 있게** 하고 접힘 상태를 기억합니다.
평상시엔 접어두고 호우 시 펼치는 사용을 상정합니다.

#### 듀얼 모니터 확장 모드

관제 PC는 듀얼 모니터가 흔합니다. **2번 모니터에 CCTV 그리드 + 위험도 타임라인을
상시 표출**하는 모드를 둡니다. 1번은 판단, 2번은 감시로 역할을 나누면 두 요구가
서로를 밀어내지 않습니다.

#### 지표에 참조값 부여

숫자만 있으면 판단이 안 됩니다.

| 지표 | 나쁜 예 | 좋은 예 |
|---|---|---|
| 위험등급 | `경계` | `경계` **(평시 대비 ↑2단계)** |
| 강수 | `12mm/h` | `12mm/h ↑` **(주의 기준 20mm/h)** |
| 하천 | `2.1m` | `2.1m` **(주의 3.0m)** |
| 인원 | `39명` | `39명` **(평시 이 시간대 12명)** |

⚠️ 평시 기준값은 운영 데이터가 쌓여야 산출됩니다. 그전에는 **「수집 중」**으로 표시합니다.

#### 정보를 더 넣자는 요구가 나올 때의 판정 기준

운영 중 반드시 추가 요청이 들어옵니다. 아래로 판정합니다.

1. **3초 안에 봐야 판단이 바뀌는가** → 예면 1층(상태바), 아니면 3층 이하
2. **1층이 이미 7개인가** → 그렇다면 **하나를 빼야 하나를 넣습니다**
3. **다른 화면에서 볼 수 있는가** → 그렇다면 상황판에 넣지 않습니다

이 기준을 문서에 남기는 이유는, 근거 없이 지표가 늘어나는 것을 막기 위해서입니다.

| 상태 | 표시 | 왜 구분하나 |
|---|---|---|

| 갱신 지연 | 「갱신 지연」 배지 | 기대 주기의 2배를 넘겼으면 **실제로 관측되지 않고 있습니다** |
| **반영 대기** | 「반영 대기」 배지 | S-80에서 방금 「상시」로 바꿨고 아직 순회 목록에 안 들어갔습니다 |
| 경과 시간 | 「방금」/「40분 전」 | 지금 등급이 방금 것인지 15분 전 것인지 |

> ### ⚠️ 「상시」 배지는 관측 중이라는 뜻이 아닙니다
> 설정과 실제 동작이 어긋나는 순간을 화면이 감추면 안 됩니다. 그래서
> **워처가 실제로 들고 있는 목록**과 S-80 지정을 대조해 「반영 대기」로
> 드러냅니다.

#### 집중 감시

상시 순회 15분 주기로는 **결빙·낙하물·사고 잔해**에 대응할 수 없어, 지점 한 곳을
**60초 주기**로 반복 관측합니다.

| 제약 | 근거 |
|---|---|
| **한 번에 한 지점** | 분석기가 하나뿐이라 여럿을 동시에 돌리면 상시 순회가 굶습니다 |
| **30분 자동 종료** | 켜 두고 잊으면 CPU를 계속 뭅니다 |
| 대상 해제 시 중지 | S-80에서 노면 사용을 끄면 감시도 멈춥니다 |

#### 지점별 관측 이력 (v4.5 추가)

**카드를 누르면 그 지점의 관측 이력이 아래 표로 열립니다.**

```
┌─ 관측 이력 · 부산역 광장            5회   [✕ 닫기] ─┐

│ 2026-08-14 21:20:00   분석 실패     —     0   상시 순회│
│ 2026-08-14 22:20:00   관찰          1     4   직접 실행│

```

각 **카드에도 추이 막대**가 들어갑니다(관측 1회 = 막대 1개, 빨강은 분석 실패).

**왜 필요한가** — 「지금 손상 4건」만으로는 **나빠지고 있는지** 알 수 없습니다.
어제도 4건이었는지 0건에서 늘어난 것인지가 보수 우선순위를 가릅니다.

| 열 | 읽는 법 |
|---|---|
| 등급 | 정상 / 관찰 / 보수 필요 / 긴급 보수 / **분석 실패** |
| 손상 | 실패면 `—` (0건과 구분) |
| **출처** | **상시 순회 · 집중 감시 · 직접 실행** — 값이 튀는 이유를 설명합니다 |

이력은 **DB(`road_inspections`)에 영구 보관**되어 재시작해도 이어집니다.
DB를 쓸 수 없으면 메모리 이력으로 내려가며, **그때는 「메모리에만 있습니다」
경고를 표시**합니다.

| **미분석** | 아직 본 적 없음 |
| **분석 실패** | 시도했으나 프레임 0장 |
| 정상·주의·경계 | 실제 분석 결과 |

> **⚠️ 「분석 실패」를 별도로 둔 이유** — 프레임 0장인데 손상 0건이면 등급이
> 「정상」으로 나옵니다. 스트림이 끊겨 아무것도 못 본 구간을 **점검 완료로
> 오해**하게 만듭니다.

**지점을 고르면 오른쪽에 그 지점의 탐지 결과가 남습니다.** 카드에서 바로
분석을 실행할 수 있어, S-41로 옮겨 다시 고를 필요가 없습니다.

### S-30 인파 CCTV 선택 탐지 (v4.2 추가)

```
│ ──────────────────────────────────────────────────────────── │
```

**설계 판단**

| 항목 | 판단 | 근거 |
|---|---|---|
| 관측 30초 | 배회는 체류시간(기본 60초)을 보므로 짧으면 무의미하고, 60초는 관제요원이 기다리기에 김 | 30초면 밀집도·이동은 충분, 배회는 「징후」 수준 |

| **모의 데이터 경고** | 소스가 detector가 아니면 배너 | **실제처럼 보이는 것이 가장 위험** |
| 스냅샷 마스킹 | 사람 영역 픽셀화, 실패 시 미표시 | 개인정보 |
| 동시 실행 차단 | 분석기가 하나뿐 | 시간축이 뒤엉킴 |

> **⚠️ ROI(침입 금지 구역)가 없으면 침입은 탐지되지 않습니다.** 밀집도·배회만

근무 시 눈부심을 일으키고 위험등급 색상의 변별력도 떨어집니다. 이 안내를 화면에
고정 표시합니다.

## 8. 알림·통보 체계 — 3계층

v1~v2까지 "알림"은 하나였습니다. 실제로는 성격이 다른 세 가지입니다.

| 계층 | 대상 | 수단 | 되돌리기 | 권한 | 화면 |
|---|---|---|---|---|---|
| **① 내부 통보** | 담당 부서·상황실 | 문자·알림톡 | 가능 | 관제요원 단독 | S-03 |
| **② 기관 통보** | 112·119·재난상황실·도로관리청 | 연계 API·유선 | 정정 가능 | 관제요원 단독 | S-03 |
| **③ 주민 경보** | 불특정 다수 | **CBS 재난문자** | **불가** | 2인 승인 + 지자체 권한 | S-12 · S-50 |

**③은 화면도 절차도 분리해야 합니다.** 잘못 나간 재난문자는 되돌릴 수 없습니다.

⚠️ **CBS는 지자체 권한이며 행안부 시스템으로 발송됩니다. 우리가 직접 송출할 수 없습니다.**

**주민 문자 2인 승인의 예외** — 위험등급 「심각」일 때 관제요원 단독 발송을 허용하는 대안을 **설정으로 열어 둡니다**(기본 꺼짐). 신속성과 신중함 중 어느 쪽을 택할지는 지자체 운영규정에 달렸습니다.

## 9. 공통 사항

### 9-1. 디자인 토큰

기존 `styles.css`의 CSS 변수 체계를 유지합니다. 관제 화면에 적합한 다크테마이고 위험등급 색상이 이미 잡혀 있습니다.

| 용도 | 값 |
|---|---|
| 배경 / 패널 / 경계 | `#0f1420` / `#171d2c` / `#2a3348` |
| 위험등급 관심→심각 | `#3fb950` → `#d4a017` → `#e8843b` → `#e5484d` |

### 9-2. 반응형 — 3등급제

**전면 반응형은 채택하지 않습니다.** 관제 시스템은 고정 자리·고정 장비에서 운용되므로,
필요한 화면에만 적용합니다. 먼저 세 가지를 구분합니다.

| 구분 | 내용 | 적용 범위 |
|---|---|---|
| **① 유동 레이아웃** | 고정 px 금지, 상대 단위·유동 그리드 | **전 34화면 필수** |
| **② 반응형 재구성** | 폭에 따라 화면 구조 변경(breakpoint) | B·C군만 |
| **③ 모바일 최적화** | 터치·세로 화면 전용 설계 | B군만 |

①은 반응형이 아니어도 필수입니다. 관제 PC 해상도가 1920·2560·4K·듀얼모니터로
제각각이고, 접근성의 「확대 시 재배치」 요건도 여기에 걸립니다.

#### A군 — 데스크톱 고정 (16화면) · 반응형 불필요

S-01 · S-02 · S-10 · **S-11** · S-20~23 · S-30~33 · S-40~41 · S-81 · S-91

| 이유 | 내용 |
|---|---|
| 운용 환경 | 3교대 상황실은 고정 자리·고정 장비. 근무자가 폰으로 관제하지 않음 |
| 정보 밀도 | 반응형은 좁은 폭에서 밀도를 희생하는 타협. 그 타협을 넓은 화면까지 끌고 오면 본래 화면이 나빠짐 |
| 입력 방식 | **S-81 ROI 설정은 정밀 좌표 클릭** — 터치로 불가 |
| ⚠️ 안전 | **S-11 시설물 제어는 모바일 차단이 오히려 안전 요건.** 작은 화면 오터치로 차단막 명령이 나가면 안 됨 |

#### B군 — 모바일 필수 (4화면)

| 화면 | 이유 |
|---|---|
| **S-43 시민 제보 접수** | 현장에서 폰으로 촬영·제보. 모바일이 아니면 기능이 성립하지 않음 |
| **S-03 이벤트 상세** | 현장 확인 나간 직원이 그 자리에서 조치 기록 |
| **S-50 알림 승인 대기함** | 야간·휴일에 폰으로 승인이 안 되면 **2인 승인 구조 자체가 무력화됨** |
| S-00 로그인 | 위 세 화면의 진입점 |

#### C군 — 태블릿까지 (14화면) · 모바일 최적화 불필요

S-04 · S-12 · S-34 · S-42 · S-51 · S-60 · S-61 · S-70 · S-80 · S-82~85 · S-90

#### breakpoint 정의

| 등급 | 관제PC 1600+ | 노트북 1200~1600 | 태블릿 ~1024 | 모바일 ~640 |
|---|---|---|---|---|
| **A** | 기준 설계 | 유동 축소만 | — | — |
| **B** | 기준 설계 | 유동 축소 | 세로 재배치 | 단일 열·터치 |
| **C** | 기준 설계 | 유동 축소 | 세로 재배치 | — |

**QA 조합이 136가지에서 60가지로 줄어듭니다.** 그만큼을 A군 정보 밀도를 다듬는 데 씁니다.

- 표·타임라인·차트는 등급과 무관하게 **자체 가로 스크롤 컨테이너**에 넣습니다

### 9-3. 웹 접근성

> 공공기관 납품 시 웹 접근성 품질인증(WA) 요구 가능성이 있습니다.
> ⚠️ **적용 의무 범위와 근거 법령은 검증하지 못했습니다 — 발주 사양서 확인이 필요합니다.**
> 다만 사후 적용은 화면 전면 재작업이므로 설계에 반영해 둡니다.

| 항목 | 현재 | 조치 |
|---|---|---|
| 색상만으로 정보 전달 금지 | ❌ 위반 (위험등급) | 등급 텍스트·아이콘 병기 |
| **지도 정보의 텍스트 대체** | ❌ | 이벤트 큐가 항상 같은 정보 제공 |
| 키보드만으로 조작 | ❌ 모달이 마우스 전용 | focus trap · ESC 닫기 |
| 대체 텍스트 | ❌ | 전 화면 점검 |
| 명도 대비 4.5:1 | ⚠ 미확인 | `--muted #93a0bb` 측정 필요 |
| 초점 표시 | ⚠ 미확인 | `:focus-visible` 명시 |
| 반응형 | ❌ | 9-2절 |

**반응형은 접근성과 맞물립니다.** 확대 시 가로 스크롤 없이 재배치되어야 하는 기준이 있어, 반응형으로 만들면 접근성 비용이 줄어듭니다.

### 9-4. 망분리 대응

| 항목 | 문제 | 조치 |
|---|---|---|
| CCTV 재생 라이브러리 | 외부 CDN 의존 → 폐쇄망에서 영상 안 나옴 | **로컬 번들** (난이도 하) |
| 지도 배경 | 외부 지도 서비스는 폐쇄망에서 안 뜸 | **지자체 GIS 서버 연계 1순위** |
| 외부 API (KMA·HRFCO·SOLAPI) | 외부 통신 차단 | 연계 방식 재설계 필요 |

⚠️ **망분리 여부가 이 세 가지를 모두 좌우합니다.** 가장 먼저 확인해야 할 인프라 조건입니다.

### 9-5. 개인정보

| 기능 | 쟁점 | 권고 |
|---|---|---|
| 배회 탐지 | 개인 행동 추적 | PIA 대상 여부 확인 필요 |
| **성별·연령 추정** | 민감정보 추정 | **넣지 않기를 권고** |
| **시민 제보 사진** | 사람·차량번호 포함 가능 | 접수 시 **자동 마스킹** |
| 자원 위치 추적 | 직원 위치정보 | **1차 범위 제외** |

성별·연령 추정은 서울시 사례에 있지만 **통신사 데이터 기반**이고 우리는 **CCTV 영상 분석**입니다. 같은 정보라도 취득 방식이 달라 쟁점 크기가 다릅니다. 주민 설명회·정보공개 청구 상황을 염두에 두고 넣지 않는 편을 권합니다.

```
⑥  통합 상황판                  S-01 (지도 중심)            ✅ 완료
⑦  알림 승인 + 통보 이력         S-50 · S-51                ✅ 완료
⑧  시설물 제어 — 「권고」 모드만  S-11  ★                    ✅ 완료
⑨  설정 화면군                  S-80~S-85                  ✅ 완료
⑩  시민 제보 접수               S-43 (도로 데이터 확보)      ✅ 완료
⑪  모델 운영 · 통계 리포트       S-61 · S-60                ✅ 완료
─────────────────────────────────────────────────────────────
⑫  자원·출동 관리               S-10                       ❌ 미착수
⑬  교대 인수인계 · CBS 요청서    S-04 · S-12                ❌ 미착수
⑭  외부 연계                   S-70                       ❌ 규격 미확보 — 착수 불가
⑮  접근성 대응                  전 화면                     ❌ 미착수

    CCTV 통합 등록·관리          S-80 · S-81 확장            ✅ 완료
    3개 도메인 상시 탐지          service/continuous.py       ✅ 완료
    인파 CCTV 선택 탐지          S-30                       ✅ 완료
```

**병행 가능 (설계 확정과 무관, 즉시 착수)**
- 무인증 알림 발송 엔드포인트 임시 차단 — ⑦ 완성 전까지의 응급조치
- CDN → 로컬 번들 (9-4절)

**순서에 대한 두 가지 판단**
- **⑤가 ⑥보다 앞**입니다. 상황판이 이벤트 위에 올라가는 구조라 뒤바뀌면 두 번 만듭니다
- **⑧을 앞으로 올렸습니다.** 「권고」 모드만이라면 기술적으로 알림의 변형이라 부담이 작은데, 제안에서 갖는 무게는 큽니다

> ⚠️ 기간은 산정하지 않았습니다. 투입 인력에 따라 달라지므로 개발부와 협의 후 별도 산정이 필요합니다.
