## 0. 결론 요약 (두괄식)

- **골격은 이미 상당 부분 존재합니다.** 사양의 ②Perception → ③VLM → ④Semantic → ⑤Risk → ⑥Decision 5단 구조가 `crowd/` 모듈에 이미 구현돼 있습니다. 완전한 신규 개발이 아니라 **기존 파이프라인의 확장·교체** 작업입니다
- **탐지 7종 중 현재 커버되는 것은 2종**(군중급증·패닉움직임)입니다. 나머지 5종(배회·침입·폭력징후·쓰러짐·위험물투기)은 신규 개발 대상이며, **난이도 편차가 매우 큽니다**
- **GPU 없이 가능한 범위와 불가능한 범위가 명확히 갈립니다.** 배회·침입은 CPU로 충분하고, 폭력징후·쓰러짐은 행동인식 모델(TimeSformer/Video Swin)이 필요해 사실상 GPU가 필요합니다
- **하드웨어 미보유 항목이 있습니다** — Stereo CCTV, 환경센서는 현재 없습니다(2D LiDAR은 범위 제외). 이 입력에 의존하는 기능은 하드웨어 확보가 선행되어야 합니다
- **⚠️ 개인정보 이슈가 새로 발생합니다** — 배회 탐지는 "동일 인물의 체류시간 추적"이라 기존 익명 집계와 성격이 다릅니다(5절)

| **Panic-like movement (패닉)** | ✅ **구현됨** — `PANIC_DISPERSION` | 기존 `dispersion`/`divergence` | ❌ 불필요 |
| **Loitering (배회)** | ❌ 없음 | 추적ID별 체류시간(`dwell_time`) 누적 | ❌ **불필요** |

## 2. GPU 없이 가능한 범위 (권장 우선 착수)

침수 도메인에서 확인한 것처럼, **실제 필요 기능을 정확히 보면 GPU가 불필요한 경우가 많습니다.**

### 2-1. 핵심 발견 — SAM3 마스크는 거의 쓰이지 않는다

`crowd/` 전수 조사 결과:

| SAM3 출력 | 실제 소비처 |
|---|---|
| `person_count` | 화면 표기, VLM 프롬프트 |
| `boxes` | **heatmap·추적기 (핵심)** |
| `density`(마스크 합) | 스칼라 1개(화면 점유율) + 좌표 1개(핫스팟)로 **즉시 붕괴** |

- `heatmap.py:31-37` — `boxes`만 사용. 주석에도 *"SAM3든 YOLO든 무엇이 만들었든 상관없이 박스 배열로 동작"* 명시
- `behavior_tracker.py:32-54` — 박스만으로 ByteTrack → 궤적·속도 → surge/dispersion/divergence
- `sam3_pipeline.py:127` — 추적기에 **더미 신뢰도 `np.ones()`** 를 넣고 있음(SAM3의 `scores`를 버림)

→ **사람 검출기(박스)만 있으면 동일 산출물 생성 가능.** 3.45GB GPU 모델 불필요.

### 2-2. GPU 없이 구현 가능한 항목

| 기능 | 방법 | 근거 |
|---|---|---|
| 사람 검출 | torchvision SSDLite/FasterRCNN-MobileNetV3 (**BSD**) | 침수에서 검증된 접근. AGPL 회피 유지 |
| **Loitering(배회)** | ByteTrack ID별 체류시간 누적 → 임계 초과 판정 | 추적기가 이미 ID를 부여 중 |
| **Intrusion(침입)** | `common/roi.py`의 `point_in_polygons()` + 발점 좌표 | **ROI 인프라가 이미 존재** |
| Crowd Surge / Panic | 기존 로직 유지 | 이미 구현됨 |
| 밀집도(CSRNet 대체) | `grid_density()` 가우시안 누적 | 이미 구현·CPU 동작 |
| Optical Flow | OpenCV Farnebäck (CPU) | opencv 이미 의존성 |

### 2-3. 현재보다 **성능이 좋아질** 수 있는 지점 (구조적 근거)

단순 대체가 아니라 지금 구조의 약점을 메울 수 있습니다.

1. **신뢰도 정보 복원** — 현재 추적기가 더미 `np.ones()`를 받아 ByteTrack의 2단계 매칭(고신뢰/저신뢰 분리)이 무력화된 상태입니다. 실제 검출 점수를 넘기면 **가림(occlusion) 상황 추적 안정성 개선**
2. **시간적 앙상블** — 관제는 30fps 실시간이 불필요합니다(현재도 `FRAME_STRIDE=15`). 남는 연산으로 다중 프레임 평활화 → 단일 프레임보다 안정적 밀집도
3. **다중 스케일 추론** — 인파 장면은 원경 인물이 작아 검출이 어렵습니다. 타일 분할 추론으로 원경 검출률 개선

**⚠️ 다만 "더 좋다"는 아직 가설입니다.** 데모 케이스에 정답값(**39명 검출 / 최대위험 0.438 / 경보 5건**)이 남아 있어 정량 비교가 가능하므로, **반드시 실측 검증 후 판단**해야 합니다. 침수에서 "val F1 0.9365"라는 좋은 지표에도 실사용에서 무너졌던 전례가 있습니다.

## 3. GPU 또는 하드웨어가 필요한 범위

| 항목 | 필요한 것 | 대안 |
|---|---|---|
| Assault-like(폭력징후) | 행동인식 모델(TimeSformer/Video Swin) — 학습·추론 모두 GPU | 없음. CPU로는 비현실적 |
| Collapse(쓰러짐) | 자세추정 또는 행동인식 | 🔶 경량 pose(MoveNet 등)로 CPU 근사 가능하나 정확도 저하 |
| 위험물 투기 | 객체검출 + 궤적 + **소유관계 추론** | 없음. 난이도 최상 |
| Stereo CCTV / 환경센서 | **하드웨어 구매·설치** | 없음 (LiDAR은 범위 제외) |

**행동인식 학습 데이터도 별도 문제입니다** — 폭력·쓰러짐 라벨 데이터는 공개 데이터셋 확보와 라이선스 검토가 선행되어야 하며, 도로손상(Phase 2)에서 겪은 **도메인 갭 실패**가 재현될 위험이 큽니다.

`traffic_weather/perception/rainfall_provider.py`가 이미 쓰는 방식(`rainfall.type: sine|mock|kma`)을 그대로 따랐습니다. **상위 판정 로직은 어느 쪽인지 몰라도 되고**, 장비 도입 시 설정 한 줄만 바꾸면 됩니다.

| 파일 | 역할 |

| `crowd/behavior_events.py` (신규) | **배회·침입 탐지** (GPU 불필요) |
| `tests/crowd/test_field_sensors.py` (신규) | 16개 테스트 |

### 모드 전환 — 방법 2가지

**① 설정 파일** (`configs/blocks.json` > `blocks[].crowd`) — 영구 적용

```jsonc
"crowd": {
  "source":      { "type": "mock" },   // 사람 검출: mock | detector
  "environment": { "type": "mock" },   // 환경센서:  mock | device
  "stereo":      { "type": "mock" },   // 스테레오:  mock | device
  "loiter_sec": 60.0, "commercial_zone": true
}
```
장비 설치 후에는 `type`을 바꾸고 `url`을 넣으면 됩니다(파일 최상단 `_crowd_example_device` 참고). **코드 수정 불필요, 서버 재시작만 하면 적용됩니다.**

**② 대시보드 UI** — 인파관리 탭 상단의 전환 버튼 (3행 × 2버튼)

| 항목 | 선택지 |
|---|---|
| 사람 검출 | 임시데이터 / 실검출(CPU) |
| 환경센서 | 임시데이터 / 현장장비 |
| 스테레오 | 임시데이터 / 현장장비 |

⚠️ **UI 전환은 런타임 전용입니다** — 재시작하면 설정 파일 값으로 돌아갑니다. 대시보드에 **인증이 없어**(제품화 계획 P0-2) 웹 요청으로 설정 파일을 덮어쓰지 않도록 한 의도적 제한입니다. 영구 변경은 ①번을 쓰세요.

`url`이 설정되지 않은 상태에서 현장장비로 전환하면 **화면에 사유를 표시**합니다(무반응으로 보이지 않도록).

### 안전장치 (침수 도메인의 교훈 반영)

침수에서 **가짜 강수 데이터가 실측으로 오인**되는 문제를 겪었기에, 같은 실수를 막도록 설계했습니다.

| 상황 | 동작 |
|---|---|
| `type: device`인데 `url` 누락 | mock으로 되돌리고 경고 (서비스 중단 없음) |
| 장비 연결 실패 | 명시적 경고 후 mock 폴백, **`source` 필드에 `"mock"` 표기** |
| 반복 실패 | 경고 1회만 출력(로그 폭주 방지) |

### 구현된 탐지 2종

**배회(Loitering)** — 추적 ID별 체류시간 누적. 사양 ④의 규칙을 그대로 반영:
```
IF (LoiteringTime > threshold) AND (NightTime) AND (CommercialZone) THEN SuspiciousRisk ↑
```
- 통행자 오탐 방지: 일정 반경 내에 머문 경우만 배회로 판정
- 중복 경보 방지: 동일 인물 1회만 보고

**침입(Intrusion)** — `common/roi.py`의 다각형 판정 재사용. ROI 진입 순간 1회 보고.

두 이벤트 모두 사양 5절 온톨로지의 `BehaviorEvent` 속성명(`eventType`/`confidence`/`evidenceText`/`occursIn`/`detectedBy`)을 그대로 따릅니다.

### 실동작 검증에서 발견·수정한 버그 2건

**① 최초 관측 시 ROI 안에 있으면 침입으로 오판** — 분석 시작 순간 통제구역 안에 있던 사람이 전부 침입으로 보고됐습니다(60초에 3건). 침입은 **밖→안 전환**일 때만 성립하도록 수정하고 회귀 테스트를 추가했습니다.

**② mock 침입자 순간이동** — 침입자를 위치 점프로 구현했더니 ByteTrack이 다른 사람으로 인식해 새 ID를 부여 → ①의 수정과 맞물려 **침입 탐지 0건**이 됐습니다. 사인파 왕복으로 연속 이동시켜 해결.

또한 mock 통행로가 통제구역과 겹쳐 **통행자가 전부 침입으로 잡히는 문제**(60초에 23건)를 확인해, 통제구역을 통행로 밖으로 재배치했습니다.

### detector 모드 검증 완료 (2026-08-03)

데모 케이스(정답 **39명**, SAM3 결과)로 CPU 검출기를 정량 비교했습니다.

| 방식 | 검출 | 정답대비 | 소요 |
|---|---|---|---|
| SSDLite 전체 1회 | 8명 | 21% | 0.2s |
| FasterRCNN 전체 1회 | 16명 | 41% | 0.4s |
| **FasterRCNN 2×2 타일 (conf 0.4 / NMS 0.4)** | **39명** | **100%** | **1.6s** |

**전체 1회 추론은 크게 실패했습니다** — 오버레이를 보니 근경 인물만 잡고 **원경(멀리 있는 작은 인물)을 거의 놓쳤습니다.** 2-3절에서 가설로 제시했던 **타일 분할 추론**이 실제로 이 문제를 해결했습니다.

파라미터 24조합을 탐색해 최적값(2×2 / conf 0.4 / NMS 0.4)을 찾아 `DetectorCrowdSource` 기본값으로 반영했습니다.

**⚠️ 이 수치 해석 시 주의**
- 정답 39명은 **SAM3 결과이지 사람이 센 수가 아닙니다.** "정확도 100%"가 아니라 **"SAM3와 동일한 인원수"**라는 뜻이며, 개별 박스가 같은 사람을 가리키는지는 검증하지 않았습니다
- **이 한 장면(주간·고해상도 1536×1024)에 맞춘 값**입니다. 야간·저해상도 CCTV(부산 블록은 320~720px)에서는 재조정이 필요합니다
- 소요 1.6s/프레임은 실시간 30fps에 부적합하나, 관제는 프레임 샘플링을 쓰므로 실용상 문제없습니다

### ⚠️ 미검증 사항

- **`device`(현장 장비) 경로는 실제 장비로 검증된 적이 없습니다.** 현재는 "HTTP JSON을 반환하는 장비"라는 일반적 가정이며, 장비 규격 확정 시 `_fetch()` 교체가 필요합니다
- **mock 깊이값은 박스 높이 기반 원근 근사**입니다. 스테레오 실측이 아니므로 절대 거리(m)로 신뢰하면 안 됩니다
- 배회/침입 **임계값**(체류 120초, 반경 80px 등)은 기본값일 뿐, 현장 캘리브레이션이 필요합니다

## 4. 권장 단계별 계획

### 1단계 — CPU 기반 전환 + 즉시 가능한 탐지 2종 추가 ⭐ 권장 착수점
- SAM3 → torchvision 검출기(BSD) 교체, 데모 케이스로 정량 비교 검증
- **Loitering(배회)** 구현 — 추적ID별 `dwell_time`
- **Intrusion(침입)** 구현 — 기존 ROI 인프라 재사용
- 임계값 재보정 2곳(`config.py:31` `ALERT_DENSITY`, `semantic_risk_agent.py`의 `/60.0`)
- **성과**: GPU 없이 탐지 7종 중 **4종 커버**(급증·패닉·배회·침입)

### 2단계 — 라이브 파이프라인 연동
- 현재 `service/main.py`에 crowd 모듈 import가 **아예 없음** → 데모 뷰어 상태
- 침수 도메인과 동일하게 `runner.py`에 블록별 처리 연결
- SAM3 체크포인트 경로 버그 수정(`crowd/config.py` — `models/sam3.pt` vs `SAM3/sam3.pt`)

### 3단계 — 의미추론 고도화
- `semantic_risk_agent.py`의 가중합 → **규칙 기반 추론 엔진**으로 확장
- 사양의 온톨로지 클래스(`BehaviorEvent`/`CrowdGroup` 등) 데이터 모델 정의
- ⚠️ RDF/OWL·SPARQL 전면 도입은 **투자 대비 효과 검토 필요** — 현재 규칙 수(5종)에서는 과설계일 수 있음

### 4단계 — 예측 고도화
- 선형 외삽 → XGBoost/LSTM. **단, 학습 데이터 축적이 선행**되어야 함
- 현재 이력이 인메모리(재시작 시 소실)라 **DB 도입(제품화 P0-4)이 전제**

### 5단계 — GPU 확보 후 행동인식
- 폭력징후·쓰러짐·위험물투기
- GPU 서버 + 학습 데이터 확보 후 착수

## 5. ⚠️ 개인정보 검토가 필요한 사항 (신규 발생)

기존 crowd 기능은 **익명 집계**(인원수·밀집도)였으나, 사양의 일부 기능은 성격이 다릅니다.

- **Loitering** — *"동일 인물이 특정 상점 주변을 반복 이동"*(사양의 VLM 출력 예시)은 **개인 행동 추적**입니다. 추적ID 자체는 익명이나, 체류시간·반복방문 기록은 개인정보 해당 여부 검토가 필요합니다
- **위험물 투기** — 투기 행위자 특정이 목적이므로 개인 식별과 직결됩니다
- 사양 ⑦의 *"위험 Heatmap 데이터 공개(비식별 집계)"* 는 적절한 방향이나, **비식별 처리 기준·보존기간·접근권한**을 별도 정의해야 합니다

→ 공공기관 납품 시 **개인정보영향평가(PIA)** 대상 여부 확인을 권고합니다.

## 6. 결정이 필요한 사항

1. **1단계 착수 여부** — CPU 전환 + 배회/침입 추가. GPU 없이 탐지 4종 확보 가능
2. **하드웨어 계획** — Stereo CCTV / 환경센서 도입 예산·일정 (미확보 시 해당 기능 범위 제외). **2D LiDAR은 제외 확정**
3. **GPU 서버 확보 시점** — 폭력징후·쓰러짐의 전제
4. **RDF/OWL 전면 도입 여부** — 현재 규칙 수 대비 과설계 가능성. 단계적 확장 권고
5. **개인정보 처리 방침** — 5절 참고. PIA 대상 여부 법무·개인정보보호 담당 확인
6. **"Centum OS" 연동 규격** — 사양이 Centum OS 기반을 전제하는데, 현재 코드베이스와의 연동 인터페이스(API 규격·데이터 포맷·디지털트윈 Block 객체 스키마)가 정의되지 않았습니다. **외부 시스템 규격 확인 필요**
