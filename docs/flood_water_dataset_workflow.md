## 0. 이 작업을 하는 진짜 이유 (검증으로 확인된 사실)

당초 "잘 동작하는 기존 모델을 유지할지 vs 갈아탈지"의 문제로 봤으나, **실측 결과 기존 모델은 실제 침수 영상에서 동작하지 않았습니다.**

| 입력 | `best.pt` 결과 | 판정 |
|---|---|---|
| 맑은 날 부산 CCTV 14장 | 13장 미검출 / 1장 미미한 오탐(0.43%) | ✅ 정상 (오탐 없음) |
| 침수 영상 **원본**(레터박스 포함) | 화면 19%를 물로 검출 — **그러나 검은 여백에 마스크** | ❌ 완전 오탐 |
| 침수 영상 **레터박스 제거 후** | **0건 검출** (화면 가득 물이 찼는데도) | ❌ 완전 미검출 |

→ 즉 기존 모델의 "19% 검출"은 실제 물이 아니라 **검은 여백을 잡은 허위 신호**였고, 여백을 제거하니 실제 물은 전혀 못 잡습니다. **이 모델은 지하차도 침수 영상에서 사실상 동작하지 않습니다.**

**시사점**
- Enterprise 라이선스를 구매해 이 모델을 유지하는 선택지의 매력이 크게 떨어짐 — 성능이 검증되지 않은 모델에 라이선스 비용을 지불하는 셈
- 자체 데이터 구축(방안 B)은 라이선스 문제 해결뿐 아니라 **성능 문제 해결을 위해서도 필요**
- ⚠️ 단, 위 판정은 **영상 1건(26프레임)** 기준입니다. 야간·저조도라는 어려운 조건이기도 하므로, 다른 침수 영상으로 추가 검증하면 판단이 달라질 수 있습니다

### ✅ HydroShare "Urban Flood Image Dataset" — **1,328쌍 확보·변환 완료**

| 서브셋 | 장수 | 물 비율(평균) | 특징 |
|---|---|---|---|
| Deepflood | 1,040 | 47.2% | 다양한 도로 침수 장면(주간 컬러) |
| Sazara | 253 | 50.7% | 시가지 도로 침수, 차량 침수 |
| **WebCOOS** | **35** | 43.4% | ⭐ **고정 감시카메라** 연속 촬영 — 부산 CCTV와 가장 유사 |

**품질 검증 결과**
- 마스크가 차량·사람·연석 경계까지 정밀하게 그려져 있음(육안 확인)
- 폴리곤 변환 정확도: **IoU 0.96~0.99**, 면적 오차 0.2~1.4%p (표본 118장)
- ⚠️ 마스크는 **0/1 인코딩**입니다. 흔히 쓰는 `>127` 임계값을 쓰면 전부 비어 보이므로 주의(변환기는 `>0`으로 처리)

**논문 초록이 밝힌 난점** — 우리가 겪은 문제와 정확히 일치해 참고 가치가 높습니다: *정지 수면의 반사광*, ***젖은 노면***, *저조도*, *폭우 중 시야 저하*, *렌즈의 빗방울*

### ⚠️ 검토 보류 — Mendeley "Flood Amateur Video" (824MB, CC BY 4.0)

기술적으로는 적합하나(영상+분할이미지+색상라벨, 침수=파랑) **권리 관계가 불확실해 다운로드를 보류했습니다.**

- 원본이 **인스타그램에서 수집한 영상**
- 데이터셋 제작자가 배포 페이지에 직접 명시: *"이 데이터셋을 사용하려면 관련 저작권·프라이버시·규제 요건을 준수하는지 확인하라"* — 즉 **CC BY 4.0은 데이터셋 포장에만 적용되고, 원저작물(SNS 게시물)의 권리는 정리되지 않았음을 제작자 스스로 밝힌 것**
- 라벨 클래스에 **사람(people)**이 포함 — 식별 가능한 개인이 담겨 개인정보 이슈 소지

→ **공공기관 납품용 학습 데이터로는 권장하지 않습니다.** 사용하려면 법무 검토 선행 필요.

### 왜 YOLO-seg 폴리곤 포맷인가

**Ultralytics와 RF-DETR-Seg가 둘 다 이 포맷을 그대로 읽습니다**(RF-DETR은 `dataset_file="yolo"` 옵션). 지금 라벨링해두면 **나중에 어느 프레임워크를 고르든 데이터를 다시 만들 필요가 없습니다.** 프레임워크 종속 탈피가 이번 작업의 목적이므로 데이터도 중립 포맷으로 남깁니다.

## 2. 작업 순서

### 2-1. 데이터 수집 (2가지 경로 병행)

**경로 A — 이미 가진/확보할 침수 영상에서 추출**

```bash
python scripts/extract_flood_frames.py --video data/samples/flood/underpath_flood1.mp4 --every 3
python scripts/extract_flood_frames.py --dir <침수영상_폴더> --every 30 --set-name news_2020
```
- 레터박스를 자동 감지·제거합니다(실제로 좌 253px·우 250px 감지 확인). **이 처리 없이 학습하면 모델이 검은 띠를 물로 학습합니다.**
- 확보 가능한 소스: 과거 침수 사고 영상, 지자체 보유 자료, 뉴스 영상(⚠️ 저작권 확인 필요)

**경로 B — 비 올 때 CCTV 자동 수집** (핵심)

```bash
# .env에 KMA_SERVICE_KEY 설정 후
python scripts/collect_flood_frames.py --watch --interval 600 --threshold 3.0
```
- 침수 데이터의 최대 난점인 "호우를 기다려야 함"을 자동화로 해결합니다. 우기 동안 켜두면 데이터가 알아서 쌓입니다
- **KMA_SERVICE_KEY가 반드시 필요합니다.** 키가 없으면 기존 `build_rainfall()`은 조용히 가짜(sine) 강수로 폴백해 **맑은 날 프레임만 잔뜩 쌓입니다.** 이를 막기 위해 이 스크립트는 응답의 `source == "kma"`인지 검증하고 아니면 건너뜁니다
- 배경(물 없는) 샘플도 필요하므로 `--force`로 맑은 날에도 일부 수집해 두세요

### 2-2. 라벨링

```bash
python scripts/label_flood_water.py --folder data/datasets/flood_water_own/raw/<세트명>
```

조작: 좌클릭=꼭짓점, 우클릭=취소, **ENTER=폴리곤 확정**, `n`=저장+다음, `b`=이전, `d`=전체삭제, `q`=종료

**라벨링 지침**
- 물에 잠긴 노면의 **경계**를 따라 찍기. 단순히 젖어서 반사되는 노면은 제외(젖음 ≠ 잠김)
- 물 위 차량은 빼지 말고 물 영역을 크게 잡기 (인스턴스 분리가 아니라 **침수 면적 산출**이 목적)
- **물이 없는 프레임도 폴리곤 0개로 저장** — 배경 샘플이 있어야 오탐이 줄어듭니다(위 레터박스 오탐 사례가 배경 학습 부족의 결과일 가능성)
- ⚠️ GUI 도구라 **로컬 화면이 있는 PC에서 직접 실행**해야 합니다(원격/헤드리스 불가)

### 2-3. 학습 — ✅ **GPU 없이 CPU로 가능** (2026-08-01 확정)

**하드웨어 확인 결과**: 이 PC에는 NVIDIA GPU가 없습니다(Intel Iris Xe 내장그래픽만, `nvidia-smi` 부재). CUDA 학습은 불가능합니다.

**그런데 모델 선택을 다시 보니 CPU로 충분합니다.** 근거는 다음과 같습니다.

#### 핵심 발견 — 인스턴스 세그멘테이션이 필요 없다

`flood/water_segmentation.py`의 `WaterResult.num_instances`가 **파이프라인 어디에서도 판단에 쓰이지 않습니다**(코드 전수 확인). 실제 지표는 전부 이진 마스크 기반입니다:
- `water_area_pixels` / `water_area_ratio` — 면적
- ROI 교집합, tire-zone 분석 — 마스크 연산

즉 "물 영역이 몇 덩어리인가"는 쓰지 않고 **"어디가 물인가"만** 필요합니다. → **시맨틱 세그멘테이션으로 충분**합니다.

#### 이 전환이 두 문제를 동시에 해결합니다

| 문제 | 해결 |
|---|---|
| GPU 없음 | 경량 모델(LR-ASPP MobileNetV3)은 CPU로 학습 가능 |
| AGPL 종속 | **torchvision 세그멘테이션 모델은 BSD 라이선스** — Ultralytics 불필요 |

#### 실측 학습 속도 (본 개발 PC, 12스레드 CPU, 학습 1,200장 기준)

| 모델 | 입력크기 | 1 epoch | 40 epoch |
|---|---|---|---|
| **LR-ASPP MobileNetV3** | 384 | 4.6분 | **약 3.0시간** ⭐ |
| DeepLabV3 MobileNetV3 | 384 | 7.2분 | 약 4.8시간 |
| LR-ASPP MobileNetV3 | 512 | 7.8분 | 약 5.2시간 |

→ **하룻밤은커녕 반나절이면 끝납니다.** GPU 임차·구매가 불필요합니다.

#### 실행

```bash
python scripts/train_flood_water_cpu.py --epochs 40
python scripts/train_flood_water_cpu.py --arch deeplabv3 --size 384 --epochs 30
```

동작 검증 완료(WebCOOS 35장, 2 epoch 스모크 테스트에서 val F1 0.65 확인).

#### ⚠️ 평가 지표 주의

기존 기준선 `mask mAP50 0.864`는 **인스턴스** 세그멘테이션 지표라 시맨틱 세그멘테이션과 **직접 비교할 수 없습니다.** 여기서는 **IoU / F1(Dice)** 를 씁니다.

목표치는 이 데이터셋을 만든 원 논문이 보고한 **F1 0.9 이상**을 기준으로 삼습니다.

#### RF-DETR은 어떻게 되나

여전히 유효한 선택지이나 **후순위**입니다. DETR 계열 트랜스포머는 CPU 학습이 비현실적이고 VRAM 8GB+가 필요합니다. 시맨틱 세그멘테이션으로 목표 성능(F1 0.9)이 나오면 굳이 갈 필요가 없고, 미달할 때 GPU를 확보해 시도하면 됩니다.

## 3. 필요 데이터 규모 (추정)

⚠️ **확정치가 아닌 일반적 경험칙입니다.** 실제 필요량은 1차 학습 후 성능을 보고 조정해야 합니다.

| 단계 | 프레임 수(대략) | 비고 |
|---|---|---|
| 최소 실험 | 100~200장 | 파이프라인 동작 확인용 |
| 초기 실용 | 500~1,000장 | 단일 클래스·큰 객체라 상대적으로 적게 필요 |
| 안정 운영 | 2,000장 이상 | 주야간·강우강도·지점 다양성 확보 |

**다양성이 수량보다 중요합니다** — 같은 장면 100장보다 서로 다른 지점·시간대·조도 20장이 낫습니다. 노면 손상(Phase 2)에서 도메인 갭으로 실패한 경험을 반복하지 않으려면, **실제 운영할 부산 CCTV에서 수집한 데이터의 비중을 높여야 합니다.**

## 3-B. 학습 실행 결과 (2026-08-03)

### 최종 모델
`data/datasets/flood_water_own/runs/flood_lraspp_384_v2/best.pt`
LR-ASPP MobileNetV3 @384, **val F1 0.9392 / IoU 0.8854** (epoch 25/30) — 목표 F1 0.9 초과 달성. **CPU 학습, torchvision(BSD) 기반이라 AGPL 무관.**

### 1차 학습의 실패와 원인

1차(HydroShare 1,328장만)는 val F1 0.9365로 지표는 좋았으나 **실사용 검증에서 실패**했습니다.

- 맑은 날 부산 CCTV에서 **마른 아스팔트를 물로 칠함**(평균 28%, 최대 65% 오탐)
- 원인: HydroShare 데이터가 **전부 침수 장면**(물 비율 43~51%, 배경 0장) → 모델이 "도로 = 물"로 일반화

**교훈: val F1만 보면 안 됩니다.** 학습셋에 배경이 없으면 검증셋에도 배경이 없어, 지표는 좋은데 실사용에서 무너집니다.

| 구성 | 장수 |
|---|---|
| 침수 (HydroShare) | 1,328 |
| 배경: 옥천 폭우 영상(비는 오나 침수 없음 = 하드 네거티브) | 214 |
| 배경: 부산 맑은 날 CCTV(실제 배포 환경) | 28 |
| **합계** | **1,570장 (배경 15%)** |

도구: `scripts/add_negative_samples.py`

### 검증 결과 (3항목)

| 검사 | 기존 Ultralytics | 1차 | **v2 (최종)** |
|---|---|---|---|
| ① 실제 침수 영상에서 물 검출 | ❌ 0% | ✅ 63.4% | ✅ **37.9%** |
| ② 레터박스 여백 오탐 | ❌ 19% | ❌ 32.8% | ❌ **17.9%** |
| ③ 맑은 날 CCTV 오탐 | ✅ 통과 | ❌ 28%/65% | ✅ **0.00%** |
| **종합** | 1/3 | 1/3 | **2/3** |

**배경 샘플 추가가 ③을 완전히 해결**했습니다(28% → 0.00%). ①은 63.4%→37.9%로 낮아졌으나 과검출이 줄어든 것이며, 오버레이 육안 확인 결과 침수 노면을 정확히 덮고 차량·난간·벽은 제외하고 있습니다.

### 남은 과제 — ② 레터박스

모델이 검은 여백을 물로 오인하는 것은 **학습 데이터에 레터박스 영상이 없어서** 생긴 실제 약점입니다. 해결 경로는 두 가지:

1. **(권장·구현 완료) 전처리로 제거** — `common/video_io.py`의 `crop_letterbox()`. 여백을 잘라내면 문제 영역 자체가 사라집니다
   - ⚠️ **아직 추론 경로에 연결되지 않았습니다.** `flood/standalone_pipeline.py`처럼 임의 영상을 받는 경로에 적용 필요(라이브 CCTV는 레터박스가 없어 무관)
2. 레터박스가 있는 이미지를 배경 샘플로 추가해 재학습

**⚠️ 테스트 설계 주의**: 초기에 "좌우 18% 구간"으로 측정했는데, 크롭 후에는 그 영역이 실제 침수 도로라 정상 검출을 오탐으로 오판했습니다. 현재는 `detect_letterbox()`가 찾은 **실제 여백 영역만** 측정합니다.

### 부수적으로 잡은 버그

**Windows에서 파일명에 한글이 있으면 `cv2.imwrite`가 예외 없이 조용히 실패**합니다. 옥천 영상 추출 시 "214장 저장" 로그가 찍혔으나 실제 저장은 0장이었습니다. `extract_flood_frames.py`에 ASCII 파일명 정규화 + `imencode` 기반 저장을 적용해 해결했습니다.

## 5. 레터박스 전처리 연결 (완료)

`flood/standalone_pipeline.py`의 프레임 진입점에 `crop_letterbox` 처리를 넣었습니다.

**⚠️ ROI 충돌 주의** — ROI 좌표는 `roi_editor.py`가 **원본(크롭 전)** 프레임에서 찍은 것이라, 크롭하면 좌표가 어긋납니다. 그래서 `auto` 모드는 **도로 ROI가 없을 때만** 크롭합니다.

| `--crop-letterbox` | 동작 | 실측 검증 |
|---|---|---|
| `auto`(기본), ROI 없음 | 크롭 적용 | ✅ 좌253/우250px 감지, 여백 오탐 19% → **0.0%** |
| `auto`, ROI 있음 | 경고 출력 후 크롭 안 함 | ✅ 경고 정상 출력 |
| `on` | ROI 있어도 강제 크롭 | ✅ 정상 |
| `off` | 크롭 안 함 | — |

라이브 CCTV 경로는 레터박스가 없어 영향받지 않습니다.

## 6. 대시보드 연동 (완료)

### 구조 — 백엔드 전환 방식

기존 코드를 덮어쓰지 않고 **백엔드를 고를 수 있는 구조**로 만들었습니다. 부산 실침수 검증이 끝나기 전에 기본값을 바꾸면 검증되지 않은 모델이 운영에 들어가므로, **기본값은 기존 `ultralytics`로 유지**했습니다.

| 파일 | 역할 |
|---|---|
| `flood/water_segmentation_tv.py` (신규) | torchvision 백엔드. `WaterResult`를 그대로 반환해 하위 코드(metrics_core/risk_engine/visualization) 무수정 |
| `service/runner.py` | `water_backend` 설정으로 모델 로드·추론 분기 |

### 전환 방법

```bash
# 환경변수로 (설정파일 수정 없이)
TOT_WATER_BACKEND=torchvision python -m uvicorn tot_dashboard.service.main:app
```
또는 `configs/water_config.yaml`에 `water_backend: torchvision`.

`.claude/launch.json`에 `tot-dashboard-tv`(포트 8010) 항목을 추가해 두 백엔드를 나란히 띄워 비교할 수 있습니다.

### 운영 중 어느 모델이 도는지 확인

맑은 날에는 두 백엔드 모두 검출 0으로 똑같아 보여 구분이 안 됩니다. 라이선스가 다른 모델을 오가는 구성이라 `/api/health`에 노출했습니다.

```json
"water_segmentation": {
  "backend": "torchvision",
  "license": "BSD (torchvision)",
  "model_path": ".../flood_lraspp_384_v2/best.pt",
  "conf": 0.5, "models_loaded": 7, "blocks": 7
}
```

### 검증 결과

| 항목 | 결과 |
|---|---|
| torchvision 백엔드 모델 적재 | ✅ 7/7 블록 |
| 기본(ultralytics) 백엔드 | ✅ 7/7 블록, 기존 동작 유지 |
| 맑은 날 오탐 | ✅ 전 블록 0.0000 |
| 대시보드 4개 탭 | ✅ 정상 (콘솔 에러 없음) |
| 기존 테스트 | ✅ **55개 전부 통과** |

### ⚠️ 남은 확인 사항

- `water_tv_conf` 기본값 **0.50**은 검증셋 기준입니다. 부산 CCTV 실침수 상황에서 재조정이 필요할 수 있습니다(Ultralytics의 `water_conf: 0.10`과 의미가 달라 — 확률 임계값 vs 검출 신뢰도 — 그대로 옮기면 과검출됩니다)
- **부산 실침수 성능은 여전히 미검증**입니다. 학습 데이터가 전부 해외 장면이라, 실제 호우 데이터 확보 후 파인튜닝·재검증 전에는 기본값을 바꾸지 않는 것이 안전합니다

**현재 위치**: 라이선스 문제 없는(BSD) 모델을 **GPU 없이** 확보했고, 기존 Ultralytics 모델이 실패하던 실제 침수 영상 검출에 성공했습니다. 다만 학습 데이터가 전부 해외 장면이라 **부산 CCTV 실침수 상황에서의 성능은 아직 미검증**입니다 — 실제 호우 데이터 확보 후 파인튜닝이 필요합니다.

## 5. 결정·확인이 필요한 사항

1. **KMA_SERVICE_KEY 발급** — 공공데이터포털 기상청 초단기실황 API. 자동 수집의 전제 조건
2. **GPU 환경** — 자체 장비 구매 vs 클라우드(학습 시에만 임차). 인파관리(SAM3) 모듈도 GPU가 필요하므로 함께 검토 권장
3. **과거 침수 영상 확보 경로** — 지자체 보유 자료 요청 가능 여부. 뉴스 영상 사용 시 **저작권 확인 필수**
4. **라벨링 인력·일정** — 내부 수행 vs 외주. 물 영역은 폴리곤 작업이라 장당 1~3분 소요 예상
5. **기존 모델 추가 검증 여부** — 0절 판정은 영상 1건 기준입니다. 다른 침수 영상으로 재확인할지 결정 필요
