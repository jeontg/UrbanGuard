## 1. ③ 먼저 — 실제로 재생 테스트를 했더니 안 됐습니다

「이 환경에서 가능하게 해달라」는 요청을 받고, **추측하지 않고 직접
재생 테스트**부터 했습니다.

간이 서버를 띄우고 여러 코덱으로 인코딩한 파일을 브라우저에 실제로
올려 봤습니다.

| 코덱 | 이 환경에서 인코딩 | 브라우저 재생 |
|---|---|---|
| avc1/h264/H264/X264 | ✗ (libopenh264 인코더 없음) | — |
| **mp4v (지금까지 쓰던 값)** | ✔ | **✗ `MEDIA_ERR_SRC_NOT_SUPPORTED`** |
| **vp09 (VP9)** | **✔** | **✔** |

★ **지금까지 쌓인 클립은 전부 이 환경 브라우저에서 재생되지 않고
있었습니다.** 모듈 주석에도 이미 그렇게 적혀 있었습니다 — 「브라우저에서
바로 재생되지 않으므로 화면은 내려받기를 제공한다」. 이번에 팝업을 만들며
그 제약을 실측으로 재확인한 것입니다.

### 무엇을 했나

- 코덱을 **vp09**, 컨테이너를 **webm**으로 교체 (`core/evidence.py`)
- 실제로 만든 파일을 브라우저에 올려 **재생 확인**
- **예전 파일(mp4v)과 새 파일(webm)을 확장자로 구분**해 `Content-Type`을
  정확히 내려줍니다 — 하나로 고정하면 둘 중 하나는 항상 틀립니다
- 팝업에서 예전 클립을 열면 **「예전 형식이라 재생되지 않습니다.
  내려받기로 확인하십시오」**를 안내합니다 — 검은 화면만 보이면 고장으로
  오해합니다

## 2. ① 탐지 상자를 저장했습니다 — 도메인마다 실제 관측값만

**지어낼 수 없는 것**이라, 도메인마다 「진짜로 관측된 값」이 무엇인지부터
따졌습니다.

| 도메인 | 상자의 정체 | 지어낸 것 아님을 보장하는 방법 |
|---|---|---|
| 침수 | 세그멘테이션이 물이라고 **판정한 마스크의 경계** | 마스크 자체에서 계산(`mask_bbox()`) |
| 인파 | **그 이벤트(배회·침입)를 일으킨** 트랙의 실제 추적 상자 | 이벤트를 만든 그 트랙의 박스만 사용 |
| 노면 | YOLO가 **그 프레임에서 실제로 찾은** 손상 상자 | 대표 프레임 하나만 고르고 그 프레임 손상만 사용 |

### 노면에서 특히 조심한 것 — 프레임을 섞지 않습니다

15초 동안 여러 프레임을 봅니다. 손상이 여러 프레임에 걸쳐 있으면 상자와
화면이 서로 다른 순간의 것이 되어 **「여기서 났다」가 거짓말**이 됩니다.
그래서 **손상이 가장 많이 잡힌 프레임 하나만** 고르고, 그 프레임의 상자만
씁니다.

### ⚠️ 곁가지로 결함 둘을 더 찾았습니다

**결함 A — 노면 지점은 증거를 아예 남길 수 없었습니다.**
인파는 매 틱 `_evidence.push()`를 부르는데, **노면 상시 순회에는 그
호출이 처음부터 없었습니다.** 이번에 대표 프레임 + 상자를 넘기며 함께
고쳤습니다 — 노면 이벤트가 이제 처음으로 증거를 남길 수 있습니다.

**결함 B — 클립 증거의 도메인이 항상 빈 문자열이었습니다.**
정지영상은 이벤트에서 도메인을 받는데, 클립은 `_finish_clips`가 `""`를
그대로 썼습니다. **그 결과 지난 회차에서 넣은 도메인 필터·배지가 클립에는
전혀 안 먹히고 있었습니다.** Job에 도메인을 담아 옮기도록 고쳤습니다.

## 4. ⚠️★★ 만들면서 찾은 것 — 팝업이 실제로 열리지 않고 있었습니다

지난 회차에서 만든 팝업 마크업(`<div id="ev-modal">...`)이 **Jinja
`{% block title %}` 안에 들어가 있었습니다.**

```html
{% block title %}증거 영상 관리 — {{ org_name }} UrbanGuard
<div id="ev-modal" ...>  ← 여기부터 79줄이 title 블록 안
...
{% endblock %}
```

레이아웃에서 이 블록은 `<title>...</title>` 안에 그대로 들어갑니다.
`<title>` 안의 내용은 **브라우저가 HTML로 해석하지 않고 순수 텍스트로
취급**합니다 — 즉 **`#ev-modal`이 실제 화면(DOM)에는 존재하지 않는
상태**였습니다. `document.getElementById("ev-modal")`은 `null`을
돌려주고, 「보기」 버튼을 눌러도 **아무 일도 일어나지 않습니다.**

### 왜 시험이 못 잡았나, 그리고 어떻게 잡았나

이전 시험은 `'id="ev-modal"' in r.text`처럼 **문자열 포함 여부**만
확인했습니다. `<title>` 안이든 `<body>` 안이든 그 문자열은 응답 본문에
**똑같이 들어 있어** 시험이 통과했습니다. **구조(어느 블록에 있는가)는
문자열 검사로 못 잡습니다.**

이번에 실제로 잡은 계기는 사람이 브라우저로 열어 보려던 과정에서
`{% block title %}...{% endblock %}` 을 다시 읽다가 발견한 것입니다.
→ 기존 화면들의 관례(`index.html`의 `livemodal`처럼 **모달은 `content`
블록 끝에 둔다**)를 따라 옮겼습니다.

## 4-1. ⚠️★★ 회귀 통과 이후 찾은 것 — 침수 위험 계산이 매 틱 조용히 멈춰 있었습니다

시험은 전부 통과했지만, **실제로 서비스를 재기동해 로그를 확인하는 절차**를
그대로 따르다가 발견했습니다. 기동 이후 로그에 `[runner:` 오류가
**56회** 찍혀 있었습니다 — 지난 기동에는 0~1회였던 수치라 바로 원인을
봤습니다.

### 무엇이 문제였나

침수 지점의 탐지 상자를 기록하려고 `runner.py`의 `_update_flood()`에
아래 줄을 넣었습니다.

```python
_evidence.push_boxes(bid, boxes, (fw, fh))   # ← bid 가 여기 없음
```

`bid`는 이 메서드를 **부르는 쪽**(`_block_loop`)의 지역변수입니다.
`_update_flood(self, c, t, frame, ps)`는 `bid`를 받지 않으므로 매 틱
`NameError: name 'bid' is not defined`가 났습니다.

**이 한 줄이 메서드의 넓은 `try/except` 블록 안, 그것도 물 세그멘테이션
직후·위험 계산 직전에 있었기 때문에** 예외가 조용히 삼켜지면서
**그 아래에 있던 위험 계산 전부**(`flood_engine.update()` → 위험 점수 →
예측 → DB 기록 → `c["last_flood"]` 갱신)가 **매 틱 통째로 건너뛰어졌습니다.**
새로 넣은 상자 저장 기능만이 아니라 **침수 도메인의 핵심 기능 자체가
멈춰 있었던 것**입니다.

54/56회가 이 오류였고, 나머지 2회는 무관한 손상 프레임 처리였습니다
(정상 동작).

### 왜 시험이 못 잡았나

침수 단위 시험은 대부분 `push_boxes` 호출 자체나 `mask_bbox()` 계산
결과만 확인했고, **`_update_flood()`를 실제 러너 스레드로 끝까지 돌려
`c["last_flood"]`가 갱신되는지까지 보는 시험은 없었습니다.** `bid`가
없다는 것은 실제로 이 메서드를 호출해 봐야만 드러나는데, 그 자리를
덮는 시험이 없었던 것입니다. → 7절 확인 필요 항목에 재발 방지 시험
추가를 남깁니다.

### 어떻게 고쳤나

같은 메서드 안에서 이미 동일한 값으로 쓰이고 있던 `c["block"]["id"]`로
교체했습니다.

```python
# ⚠️ `bid` 는 `_block_loop`(호출부)의 지역변수라 여기서는 안
#   보인다 — `_update_flood` 는 `(self, c, t, frame, ps)` 만
#   받는다. `c["block"]["id"]` 가 같은 값이다(2026-08-20 확인,
#   기동 로그에서 "name 'bid' is not defined" 로 54회 잡았다).
_evidence.push_boxes(c["block"]["id"], boxes, (fw, fh))
```

### 실측으로 확인

로그를 갈아 끼우고 서비스를 재기동해 다시 지켜봤습니다.

| 시점 | `[runner:` 오류 | 내용 |
|---|---|---|
| 수정 전 | 56회 | 54회 `name 'bid' is not defined` + 2회 손상 프레임(무관) |
| **수정 후** | **1회** | 손상 프레임 처리 1회뿐 — **`bid` 오류 완전히 사라짐** |

`/api/health`의 `water_segmentation`도 `effective_backend: torchvision
· models_loaded 6 · blocks 6 · ok true`로 지점 수와 일치, 정상입니다.

> **결론**: 이번 회차의 침수 상자 기능을 넣다가 침수 위험 계산 전체를
> 껐다가, 같은 회차 안에서 실측으로 찾아 다시 켰습니다. 회귀 시험은
> 통과했지만 이 결함을 잡지 못했다는 사실을 숨기지 않고 적습니다.

큐잉·스레드 타이밍이 아니었으므로**, 공유 전역 상태를 거치지 않고
저장 함수를 직접 호출하도록 다시 작성해 결정적으로 만들었습니다.
