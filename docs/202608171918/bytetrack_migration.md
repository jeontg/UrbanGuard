## 1. 왜 옮겼나

```
FutureWarning: The `ByteTrack` was deprecated since v0.28.0.
               It will be removed in v0.31.0.
```

`supervision` 0.30 에는 **후속 추적기가 아예 없습니다.** 폐기 안내가 가리키는
곳은 **별도 패키지** 입니다.

```
Use `ByteTrackTracker` from the `trackers` package instead
(`pip install trackers`). Note: the update method is renamed from
`update_with_detections()` to `update()`.
```

**흐름 지표(속도·방향·발산도)가 전부 이 추적기 위에 올라가 있어**, 제거되면
인파 판정이 통째로 멈춥니다.

### 의존성 비용

새로 들어오는 것은 **4개뿐**이며 전부 순수 파이썬입니다.

```
trackers · rich · markdown-it-py · mdurl
```

망분리 납품에서 설치 대상이 4개 느는 것은 **API 제거로 서비스가 멈추는 것**에
비하면 작은 대가입니다.

## 2. 어댑터를 둔 이유

호출부가 **두 군데**(인파 `behavior_tracker.py`, 교통 `traffic_tracker.py`)라
각자 고치면 **한쪽만 고치는 일**이 생깁니다.

`common/tracking.py` 한곳에서 고르고, 부르는 쪽은 항상 `update()` 만 씁니다.

| 상황 | 동작 |
|---|---|
| `trackers` 있음 | **`ByteTrackTracker` 사용** (권장) |
| 없음 | `supervision.ByteTrack` 으로 되돌아감 + **경고 1회** |
| 둘 다 없음 | 추적 없이 진행 — **인원수·밀집도는 계속 나온다** |

`backend` 속성으로 **어느 쪽을 쓰는지 밖에서 볼 수 있습니다.** 결과가 달라지면
여기부터 찾게 됩니다.

## 3. ⚠️ 비교에서 잡은 것 두 가지

### ① 두 구현의 계약이 다릅니다

같은 입력으로 프레임별 `tracker_id` 를 찍어 봤습니다.

```
supervision.ByteTrack   [[1,2], [1,2], [1,2], [1,2]]
trackers                [[-1,-1], [0,1], [0,1], [0,1]]
                          ↑ 미확정에 -1 을 붙여 함께 돌려준다
```

우리 코드는 `zip(det.xyxy, det.tracker_id)` 로 **−1 도 실제 트랙으로
취급**했습니다. 그래서 첫 프레임의 여러 박스가 **「id −1 인 한 트랙」으로
뭉치고**, 다음 프레임에 진짜 id 가 붙는 순간 그 트랙의 좌표가 급점프했습니다.

```
mean_speed = 41,231 px/s      ← 정상값은 50.0
n_tracks   = 1                ← 사람은 2명
```

> ★ **속도만 재는 교체였다면 그대로 넘어갔을 것입니다.**
> ONNX 때와 같은 교훈입니다 — **바꾼 뒤에는 결과를 대조해야 합니다.**

### ② 첫 수정이 인원수를 망가뜨렸습니다

어댑터에서 −1 을 **걸러 냈더니** 시험 2건이 깨졌습니다.

```
person_count = 0        ← 첫 프레임에 사람이 없다고 나옴
```

**사람을 세는 일과 속도를 재는 일은 다릅니다.** 추적이 아직 확정되지 않았다고
**화면의 인원수가 0이 되면 안 됩니다.**

되돌려서 이렇게 나눴습니다.

| 용도 | 처리 |
|---|---|
| 인원수 · 밀집도 · 이벤트 | **모든 검출** 사용 |
| 속도 · 방향 · 발산도 | **확정 트랙만** (`is_confirmed()`) |

## 4. 교체 전후 검증

같은 입력에 두 구현을 돌렸습니다.

| 구현 | n | 속도 | surge | dispersion | divergence |
|---|---|---|---|---|---|
| `supervision.ByteTrack` | 2 | 50.0 | 1.00 | 1.00 | 35.4 |
| `trackers.ByteTrackTracker` | 2 | 50.0 | 1.00 | 1.00 | 35.4 |

**완전히 같습니다.** 교체로 판정이 달라지지 않습니다 — 그동안 쌓인 관제 이력과
그대로 비교할 수 있습니다.

---

## 5. 기록해 둔 동작 차이

**`trackers` 는 속도 산출에 프레임이 하나 더 필요합니다.**

| 구현 | 속도가 나오기까지 | 5fps 기준 |
|---|---|---|
| `supervision` | 2프레임 | 0.4초 |
| `trackers` | **3프레임** | **0.6초** |

첫 프레임에 미확정(−1)을 주기 때문이며, `minimum_consecutive_frames=1` 로도
바뀌지 않습니다(실측 확인). **관제상 무시할 만하지만 숨기지 않습니다.**

기존 시험이 「2프레임」에 묶여 있어 깨졌는데, **지키려는 것은 「움직이면 속도가
나온다」이지 프레임 수가 아니므로** 프레임 수에 안 묶이도록 고쳤습니다. 추적기를
또 바꿔도 안 깨집니다.

## 7. 시험

| 구분 | 결과 |
|---|---|
| 신규 시험 | **9건** |
| 전체 회귀 | **1,050건 통과 · 3건 건너뜀 · 실패 0** |
| 소요 | **280초 (4분 39초)** |
| 경고 | **2건 → 1건** (ByteTrack 폐기 경고 사라짐) |

### 시험이 못박은 것

- **교체 전후 지표가 같다** (핵심)
- **속도가 터무니없지 않다** — 미확정이 섞였을 때의 증상을 직접 검사
- 미확정 트랙을 **가려 낸다**
- 어댑터는 **검출을 버리지 않는다** — 인원수가 0이 되면 안 된다
- 추적기가 없어도 **인원수는 나온다**
- 추적 실패는 **한 프레임을 건너뛸 뿐**이다
- **폐기 경고가 새어 나오지 않는다**
