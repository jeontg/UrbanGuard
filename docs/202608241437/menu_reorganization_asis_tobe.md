## 0. 결론 먼저

○ 2026-08-24에 "설정 12항목·관리자 6항목"이 뭉쳐 있던 것을 6개 묶음으로
　나눠 **11 → 15묶음**으로 정리했습니다. 뚱뚱한 묶음 문제는 풀렸지만,
　**묶음이 늘어난 만큼 세로 길이도 늘었고**, 더 근본적으로 **설계서가
　정한 원칙과 어긋난 부분이 그대로 남아 있습니다**

○ ★ **가장 큰 문제 — 메뉴가 실제 업무 흐름을 가로지릅니다.** 사건 하나를
　처리하는 흐름(조치 → 승인 → 결과 확인)이 "이벤트"·"알림·통보" 두
　대분류로 갈라져 있습니다. 설계서가 직접 "화면 이동이 골든타임을
　깎는다"고 명시한 바로 그 상황입니다

○ ★ **두 번째 문제 — 도메인이 상단 절반을 차지합니다.** 설계서는
　"관제요원은 도메인별로 근무하지 않는다"고 명시하는데, 메뉴는 침수·
　교통위험·인파관리·도로 노면 관리 4개 묶음이 가장 눈에 띄는 자리에
　있습니다

○ **셋째 — 화면번호 체계가 무너져 있습니다.** 설계서에 없는 화면 12개,
　번호가 아예 없는 화면 2개, 번호가 겹치는 화면 2개, 구현됐는데 메뉴에
　없는 화면 4개, 접근조차 안 되는 죽은 코드 1건을 확인했습니다

○ **제안 — 15묶음을 업무 순서 기준 11묶음으로 재정리**하고, 매일 쓰는
　것과 구축·점검 때만 쓰는 것을 나눠 **평소 보이는 줄 수를 38% 줄입니다**
　（관리자 기준 55행 → 34행). 2026-08-18에 이미 확정된 신규 화면 13개가
　나중에 들어와도 **묶음 구조가 다시 무너지지 않도록** 자리를 미리
　마련합니다

## 1. 지금 구조 (As-Is)

`core/auth.py::menu_for()` 기준, 실제 화면에서 역할별로 직접 센 수치입니다.

```
◎ 관제              통합 상황판 · 멀티뷰 관제
◆ 이벤트            이벤트 목록 · 탐지 피드백 · 교대 인수인계
▣ 침수              실시간 관제 · 분석 결과 이력 · 위험도 임계값 · 알림 규칙
▣ 교통위험          실시간 관제 · 위험도 임계값 · 위험등급 관리
▣ 인파관리          실시간 관제 · 분석 사례 · 위험등급 관리
▣ 도로 노면 관리    노면 현황 · AI 탐지 실행 · 현장 제보 · 위험등급 관리
▲ 대응              시설물 원격제어                              ← 1항목
◈ 알림·통보         승인 대기함 · 통보 이력
◱ 분석              통계·성과 리포트                              ← 1항목
⚙ 카메라·지점 관리   CCTV 관리 · 위험등급 관리 · 지점 방향 관리 · 상·하류 관리
▤ SOP 관리          디지털 SOP · 위험유형별 SOP
◍ AI 모델 관리      AI 모델 운영 · 모델 설정(물 세그멘테이션) · 모델 설정(침수)
❖ 시스템·기관 관리   기관 정보·화면 · 서버 운영
◇ 계정·감사         사용자·권한 관리 · 감사 로그
▨ 오류·증거 관리     오류 관리 · 오류 코드 사전 · 증거 영상 관리 · 영상 반출 관리대장
```

**역할별 실측**(2026-08-24, `menu_for()` 직접 호출):

| 역할 | 묶음 수 | 항목 수(연결선 기준) | 화면 줄 수 | 1항목 묶음 |
|---|---|---|---|---|
| 시스템관리자(SYS) | 15 | 40 | **55행** | 대응 · 분석 (2개) |
| 부서담당자(MGR, 침수 담당) | 10 | 22 | 32행 | 대응 · 분석 · **계정·감사**(3개) |
| 관제요원(OPR) | 10 | 20 | 30행 | **교통위험** · 대응 (2개) |

※ "위험등급 관리"는 침수·인파·노면·교통위험 4개 도메인이 공용으로 쓰는
　화면이라 4곳에 같은 링크가 나타납니다 — SYS 기준 연결선 40개는 **실제
　화면 37개**를 가리킵니다.

## 2. As-Is에서 확인된 문제 5가지

| # | 문제 | 근거 | 업무에 미치는 영향 |
|---|---|---|---|
| 1 | **사건 처리 흐름이 메뉴에서 끊어짐** — 조치(이벤트 상세)와 승인(알림·통보)이 다른 대분류 | 승인 대기함 화면 자체가 "발송 요청은 이벤트 상세에서 한다"고 명시 — 이 화면은 승인만 처리 | 관제요원이 조치 후 담당자를 찾아 다른 메뉴로 이동해야 함. 설계서: "화면 이동이 골든타임을 깎는다" |
| 2 | **시설물 원격제어가 외딴 1항목 묶음** — 조치 화면에서 바로 갈 길이 없음 | 이벤트 상세 화면의 외부 링크 목록에 시설물 제어로 가는 연결 없음 | 침수 심각 시 진입차단시설을 내리려면 메뉴를 다시 훑어야 함 |
| 3 | **도메인 4묶음이 상단 절반** — 설계서 원칙과 반대 | 설계서: "관제요원은 도메인별로 근무하지 않는다" / "도메인 화면은 심층 분석용, 상시 관제는 통합 상황판·이벤트 목록에서" | 신입 관제요원이 "내가 지금 봐야 할 것"을 도메인 4곳에서 각각 찾아야 함 |
| 4 | **평소 안 쓰는 설정·관리 화면이 상시 노출** — 15묶음 중 6묶음(카메라·지점 관리 ~ 오류·증거 관리)이 구축·점검 전용인데 매번 펼쳐져 있음 | 설계서: "최소주의 원칙은 화면 전체가 아니라 항상 보이는 영역에 적용된다" | 관제요원 화면 세로 길이의 절반 이상이 그가 안 쓰는 항목 |
| 5 | **화면번호 체계가 무너짐** — 상세는 3절 참고 | `pending_tasks.md` 7-4, 설계서 §5 집계 불일치(34/35/36/37개 4가지) | 문서·제안서 작성 시 화면번호를 신뢰할 수 없음 |

| 침수 | ④ 침수 | 그대로 |
| 교통위험 | ⑤ 교통위험 | 그대로 |

## 5. 이렇게 바꾼 이유

| 변경 | 이유 |
|---|---|
| **대응 + 알림·통보 → 「대응·통보」 통합** | 실제 업무에서 조치→승인→확인은 한 줄기 흐름입니다. 두 묶음으로 갈라 두면 "지금 이 사건을 어디까지 처리했나"를 메뉴 두 곳에서 확인해야 합니다. 1항목이던 "대응" 묶음 문제도 함께 풀립니다 |
| **설정·관리 6묶음 → 3묶음(운영 설정/기록·감사/시스템 관리) 재통합** | 8/24에 12항목 묶음 하나를 6개로 쪼갠 것은 "찾기 쉽게"가 목적이었는데, 결과적으로 **묶음 헤더 자체가 늘어 스크롤이 오히려 길어졌습니다.** 성격이 비슷한 것끼리(카메라·지점·SOP·AI모델 = 구축 준비 / 감사·증거·반출 = 사후 기록 / 계정·오류·서버·기관 = 시스템 자체) 다시 묶습니다 |
| **감사 로그를 "기록·감사"로 재배치** | MGR에게는 "계정·감사" 묶음이 감사 로그 1개만 남는 문제가 있었습니다. 감사 로그는 증거 영상·반출대장과 마찬가지로 "사후에 들여다보는" 화면이라 그쪽이 더 맞습니다 |
| **⑨⑩⑪을 기본 접힘으로** | 설계서의 최소주의 원칙은 "화면 전체"가 아니라 "항상 보이는 영역"에 적용됩니다. 관제요원은 이 3묶음을 근무 중 거의 열지 않습니다 |
| **도메인 4묶음은 위치를 유지** | 설계서가 "심층 분석용"이라 명시했지만, 지금도 실제로 쓰이고 있어 갑자기 접으면 혼란이 큽니다. 이번에는 대응·통보 통합과 설정 재편에 집중하고, 도메인 묶음 위치 조정은 별도 검토로 남깁니다(9절) |

## 6. 앞으로 들어올 화면의 자리

2026-08-18에 제안요청서 3건을 근거로 신규 화면 13개가 이미 계획돼
있습니다(`docs/202608181305/menu_structure_plan.md`). 이번 정리는 그
화면들이 들어와도 묶음 구조가 다시 무너지지 않도록 자리를 미리
비워 둡니다.

| 계획된 신규 화면 | To-Be 자리 |
|---|---|
| 통합 타임라인 | ① 관제 |
| 유관기관 전파 현황 | ③ 대응·통보 |
| 모델 성능·오탐 분석 · 공간 분석 | ⑧ 분석 |
| 학습데이터 수집 현황·데이터셋 관리·배포 이력(3종) | ⑨ 운영 설정(또는 별도 묶음 — 8절 참고) |
| 외부 시스템 연계·연계 송수신 로그(2종) | ⑪ 시스템 관리(또는 별도 묶음) |
| 장비 상태 감시 | ⑪ 시스템 관리 |
| 매뉴얼·FAQ | ⑪ 시스템 관리 |

⚠️ 학습데이터·연계가 실제로 만들어지면 각각 3~4화면이 되어, ⑨·⑪에
넣기엔 다시 무거워질 수 있습니다. 그때는 이 두 묶음만 독립시키는 2차
조정을 권고합니다(13묶음이 되지만, 신규 기능군이 뚜렷해 찾기는 더 쉬워집니다).

## 7. 적용 단계

| 단계 | 내용 | 위험도 |
|---|---|---|
| **1** | 대응 + 알림·통보 통합 | 낮음 — 화면 이동 없이 메뉴 항목만 재배치 |
| **2** | 설정·관리 6묶음 → 3묶음 재통합 | 낮음 — 마찬가지로 메뉴 항목 재배치만 |
| **3** | 도메인 묶음 위치·구성 재검토(선택) | 중간 — 실사용자 의견 수렴 후 결정 권고 |

1·2단계는 `core/auth.py::menu_for()`의 그룹 배치만 바꾸는 작업이라
권한 로직·라우트는 전혀 손대지 않습니다. 8/24 재분류 때와 같은 방식
（`docs/202608241340/`）으로 하루 안에 적용하고 회귀 시험으로 확인
가능합니다.

## 8. ⚠️ 이 정리로도 못 푸는 것

| 항목 | 왜 |
|---|---|
| **화면번호(S-번호) 체계 정리** | 코드가 아니라 `docs/ui_design_spec.md` 공식 문서 쪽 정리가 먼저 필요합니다(9절 1~3번) |
| **도메인 묶음을 상시 노출에서 뺄지 여부** | 설계서 원칙(심층 분석용)과 실사용 관행이 부딪힙니다 — 사람 판단이 필요해 이번에는 위치를 유지했습니다 |
| **구현됐는데 메뉴에 없는 화면 4종의 노출 여부** | 의도적으로 뺀 것인지 누락인지 확인이 먼저입니다(9절 4번) |
| **죽은 코드 정리**(`routes_blocks.py`) | 메뉴 정리와 별개로, 접근 불가능한 코드를 지울지 보존할지는 별도 결정 사항입니다 |
