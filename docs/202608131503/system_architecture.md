## 1. 개요

### 1-1. 시스템 목적

부산·울산·경남 지자체를 대상으로, 기존에 따로 돌던 **침수·교통위험 / 인파관리 /
도로 노면관리** 세 가지 영상분석 기능을 **하나의 관제 화면**으로 묶은 솔루션입니다.

### 1-2. 설계를 지배한 세 가지 제약

| 제약 | 아키텍처에 준 영향 |
|---|---|
| **망분리** — 지자체 관제망은 외부 인터넷을 못 씁니다 | 지도에 외부 타일 서버를 쓰지 않고 **자체 SVG 지도**를 그립니다. CDN 의존을 두지 않습니다 |
| **CPU 전용** — GPU 없는 서버가 일반적입니다 | 도메인마다 분석 주기를 달리해 부하를 배분합니다(5절). 전 지점 상시 분석을 강제하지 않습니다 |
| **개인정보** — CCTV 영상에 시민이 찍힙니다 | 사람 영역을 검출해 **저장·표시 전에 픽셀화**합니다. 원본을 남기지 않습니다 |

### 1-3. 규모 (실측)

| 항목 | 값 |
|---|---|
| Python 소스 | **104개 파일 · 15,834줄** |
| HTML 템플릿 | 21개 |
| HTTP 경로 | **83개** |
| DB 테이블 | 12개 (컬럼 126개) |
| 자동 테스트 | **37개 파일 · 345건 통과** |

## 3. 계층 구조

패키지는 **의존 방향이 한쪽으로만 흐르도록** 나눴습니다.

```
  service  ──▶  core  ──▶  common
     │            │
     └──▶  flood / crowd / road  ──▶  common
```

| 계층 | 패키지 | 규모 | 책임 |
|---|---|---|---|
| **표현·조립** | `service` | 19개 · 3,440줄 | HTTP 라우트, 템플릿, 백그라운드 워커 기동 |
| **제품 공통** | `core` | **25개** | 권한, 이벤트, 알림, 감사, 설정, 카메라, 마스킹, **로고·정지영상·동영상저장·일괄등록·외부수집** |
| **탐지 도메인** | `flood` | 11개 | 물 세그멘테이션, 침수 위험도 |
| | `crowd` | 13개 | 사람 추적, 배회·침입, 밀집도, **분석 영역 필터** |
| | `road` | **7개** | 노면 손상 탐지, **지점별 결과 보관** |
| **부속 도메인** | `traffic_weather` | 16개 · 1,494줄 | 강우·하천·기상 제공자 |
| **공용** | `common` | 11개 · 1,470줄 | 설정 로딩, 영상 입출력, ROI |

### 3-1. 탐지 도메인이 `core` 를 모르게 한 이유

**도메인 코드는 이벤트·권한·알림의 존재를 모릅니다.** 탐지기는 「지금 이 지점이
몇 등급인가」만 계산하고, 그것을 사건으로 묶는 일은 `service/event_sync.py` 가
바깥에서 읽어 갑니다.

이렇게 한 이유는 세 도메인이 **원래 별개 프로젝트**였고 앞으로도 각자
발전하기 때문입니다. 이벤트 정의가 바뀌어도 탐지 코드는 건드리지 않습니다.

### 3-2. 경계에서의 형식 변환

기존 파이프라인은 `blocks.json` 구조를 그대로 기대합니다. 카메라를 DB로 옮기면서
**탐지 코드를 고치는 대신** 경계에서 변환합니다.

```
DB (cameras + camera_domains + camera_rois)
        │
        │  core/cameras.py :: to_block_dict() / to_roi_config_dict()
        ▼
기존 파이프라인이 기대하는 dict 구조
```

위험이 큰 탐지 코드를 건드리지 않는 편이 안전하다고 판단했습니다.

---

### 3-3. 운영 데이터는 소스 트리 밖에 둔다

화면에서 올린 파일은 `data/` 아래 둔다. `static/` 에 쓰면 **배포로 코드를
덮어쓸 때 운영 중 올린 자료가 날아간다.**

| 폴더 | 내용 | 서빙 |
|---|---|---|
| `data/branding/` | 기관 로고 (S-85) | `/branding/logo/{name}` — **공개 경로** |
| `data/videos/` | 분석용 동영상 (S-80) | 서빙하지 않음. 분석기가 파일로 읽음 |

둘 다 형상관리에서 제외했다 — 지자체마다 다른 자료가 코드에 섞이면 안 된다.

### 3-4. ROI 정지영상은 파이프라인과 무관하다

ROI는 **설정 작업**이지 관제가 아니다. 예전에는 탐지 파이프라인이 저장한
프레임에만 의존해, 상시 탐지가 켜진 침수 카메라 말고는 화면이 비었다.
동영상을 새로 등록하면 ROI를 그릴 수조차 없었다.

`core/snapshot.py` 가 **소스에서 직접 한 장 뽑는다** — 동영상은 15% 지점,
HLS는 유효 프레임까지 최대 40장 읽는다.

## 4. 요청 처리 흐름

### 4-1. 모든 요청은 가드를 지납니다

```
HTTP 요청
   │
   ▼
[ PUBLIC 경로인가? ]──예──▶ 통과 (/login, /static, /api/health)
   │ 아니오
   ▼
[ 세션 쿠키 검증 ]──실패──▶ 화면: 로그인 리다이렉트 / API: 401
   │ 성공
   ▼
[ 임시 비밀번호 상태? ]──예──▶ 비밀번호 변경 화면으로 강제 이동
   │ 아니오
   ▼
[ 경로 규칙표(RULES) 조회 ]
   │
   ├─ 규칙 없음 + /api  ──▶ **403 (기본 거부)**
   ├─ 규칙 없음 + 화면   ──▶ 라우트 의존성이 세부 판정
   └─ 규칙 있음 ──▶ [ 권한 매트릭스 판정 ] ──실패──▶ 403
                              │ 성공
                              ▼
                          라우트 실행
```

**핵심은 「기본 거부」입니다.** 규칙표에 없는 `/api` 경로는 통과시키지 않습니다.
새 API를 만들면서 규칙 등록을 잊으면 **동작하지 않으므로**, 보안이 빠진 채
조용히 열려 있는 상태가 생기지 않습니다.

> 이 설계는 실제 사고에서 나왔습니다. 알림 발송 API에 인증이 빠져 있었고,
> 엔드포인트마다 의존성을 붙이는 방식이었기 때문에 **빠뜨린 것을 아무도
> 몰랐습니다.** 그래서 한곳에서 판정하는 미들웨어로 바꿨습니다.

### 4-2. 권한 판정

3역할 × 15자원 × 4행위를 코드로 표현한 매트릭스입니다(`core/roles.py`).

| 역할 | 범위 |
|---|---|
| `SYS` 시스템관리자 | 전 기능. 정보통신 부서 |
| `MGR` 부서담당자 | 담당 도메인만. 안전총괄·도로 부서 |
| `OPR` 관제요원 | 전 도메인 관제·탐지 실행. 설정 불가 |

**도메인 범위 검사는 `MGR` 에만 적용합니다.** 관제요원은 상황실에서 세 도메인을
모두 봐야 하므로 도메인으로 가르지 않습니다.

## 5. 동시성 · 스레드 모델 ★

가장 주의가 필요한 부분입니다. 영상 분석이 **블로킹 I/O + CPU 연산**이라
FastAPI의 비동기 모델만으로는 처리할 수 없습니다.

### 5-1. 스레드 구성

```
 [메인 프로세스 — uvicorn]
   │
   ├─ 이벤트 루프 (HTTP 요청 처리)
   │     └─ 무거운 동기 작업은 run_in_threadpool() 로 넘김
   │           · 인파 선택 탐지 (30초)
   │           · 노면 선택 탐지 (15초)
   │
   ├─ PipelineRunner (침수) ─┬─ 지점별 워커 스레드 × N   ← 약 5 fps 연속
   │                        └─ 지점 7개소면 스레드 7개
   │
   ├─ CrowdContinuousWatcher ─── 지점별 워커 스레드 × M  ← 지점당 5초 간격
   │
   ├─ RoadContinuousWatcher ──── 단일 스레드가 순회      ← 지점당 15분
   │     └─ 관측 프레임을 학습 수집기로도 넘김 (기본 꺼짐)
   │
   ├─ RoadFocusWatcher ───────── 지점 1곳 집중 감시      ← 60초 주기·30분 시한
   │                             ※ 한 번에 하나만 (분석기 공유)
   │
   └─ EventSync ──────────────── 단일 스레드            ← 20초 주기

 [지점별 최신 결과]  road/results.py — 상시 순회·집중 감시·선택 실행이 같은
                    저장소를 채운다. ⚠️ 메모리라 재시작하면 사라진다.
```

### 5-2. 도메인마다 방식을 달리한 근거

| 도메인 | 방식 | 근거 |
|---|---|---|
| 침수 | 지점별 스레드, 연속 | 물 확산은 초 단위로 변합니다. 또 단일 스레드로 4개 이상 스트림을 돌리면 추적점이 2개도 안 쌓여 속도가 0으로 읽힙니다 |
| 인파 | 지점별 스레드, 표본 | **추적과 배회 판정은 끊기지 않는 시간축이 전제**입니다. 한 스레드가 지점을 번갈아 보면 추적 ID가 매번 끊겨 배회를 영영 못 잡습니다 |
| 노면 | 단일 스레드 순회 | 포트홀은 분 단위로 변하지 않습니다. 1회 분석에 15초가 걸려 동시 실행이 오히려 해롭습니다 |

### 5-3. 겪은 문제와 대응

| 문제 | 대응 |
|---|---|
| **기동 직후 첫 순회가 통째로 헛돌았습니다.** 침수 7개소가 스트림을 열고 모델도 올라오는 시점에 노면이 끼어들어 프레임을 못 받음 | 기동 유예(인파 20초 / 노면 60초) + 1회 재시도 |
| **`threading.Thread` 상속 시 `self._stop` 속성이 내부 메서드 `_stop()` 을 가림.** `is_alive()`·`join()` 만 불러도 `TypeError` | 속성명을 `_stop_ev` 로 변경 (3개 클래스) |
| 인파 분석기가 하나뿐이라 동시 실행 시 시간축이 뒤엉킴 | `threading.Lock` 으로 직렬화, 충돌 시 409 응답 |
| 상시 루프와 선택 탐지가 분석기를 공유해 **30초 관측에 「체류 190초」가 섞임** | 관측 시작 시점의 이벤트를 미리 걸러 냄 |
| **같은 카메라를 침수·인파가 상시로 보고 있으면 노면 분석이 즉시 거부됨**(실측: 0프레임·0.0초) | 2초 쉬었다 1회 재시도 + 화면에 사유 안내 |
| 카메라 등록 실패 시 업로드한 동영상만 남고 **이전 영상이 지워짐** | 임시 이름으로 받아 두고 등록 성공 후 확정 |
| ★ **DNS 장애 중 서비스가 세그폴트로 죽음**(2026-08-12 밤, exit 139). 호스트가 풀리지 않는 동안 8개 스레드가 1초마다 재접속하며 FFmpeg 컨텍스트를 초당 8개씩 생성 | `common/stream_guard.py` — **호스트가 안 풀리면 FFmpeg 를 부르지 않음** + 재접속 간격 지수 증가(1→60초). 실측: DNS 실패 중 `VideoCapture` 호출 **0회** |
| 세그폴트는 파이썬에서 잡을 수 없음(예외조차 오지 않음) | `scripts/serve.py` 감시 프로세스가 비정상 종료를 감지해 재기동. 실측: 강제 종료 후 **5초 만에 복구** |
| 감시 프로세스가 **로그 한 줄에 죽음** — 한국어 Windows 콘솔이 cp949 라 「—」에서 `UnicodeEncodeError` | 콘솔을 UTF-8 로 재설정 + 출력 실패를 삼킴. 서비스를 지키려 띄운 감시가 로그 때문에 죽으면 의미가 없음 |

### 5-4. ⚠️ 알려진 한계

- **단일 프로세스 구조입니다.** uvicorn 워커를 늘리면 워커마다 분석 스레드가
  중복 기동돼 CPU가 배로 듭니다. 현재는 워커 1개 전제입니다.
- **상시 탐지 대상 변경 — 노면은 즉시, 인파는 재시작입니다.**
  노면은 `core/config_rev.py` 신호로 S-80·S-81 저장 즉시 목록을 다시 읽습니다
  (자고 있던 순회 스레드를 깨움). 인파는 카메라마다 ByteTrack 추적기를 두는데
  실행 중 교체하면 배회 타이머가 초기화돼 탐지를 놓치므로 그대로 두었습니다.
- **수평 확장 경로가 없습니다.** 지점이 수십 개소로 늘면 분석을 별도 워커
  프로세스로 분리하고 큐(Redis/RabbitMQ 등)로 연결하는 구조가 필요합니다.
- ⚠️ **네이티브 크래시를 근본적으로 막지는 못했습니다.** 스트림 디코딩이 같은
  프로세스 안에 있어, FFmpeg/OpenCV 가 죽으면 서비스 전체가 함께 죽습니다.
  현재는 **(a) 방아쇠를 줄이고 (b) 죽으면 되살리는** 두 겹으로 대응합니다.
  근본 해결은 디코딩을 별도 프로세스로 격리하는 것이며 구조 변경이 큽니다.
- ⚠️ **감시 프로세스는 서버 재부팅을 넘지 못합니다.** 운영 납품에서는 Windows
  서비스(NSSM 등) 또는 작업 스케줄러 등록이 필요합니다.

## 6. 데이터 흐름

### 6-1. 탐지 → 이벤트 → 대응

```
 CCTV(HLS)
    │
    ▼
 [ 탐지 도메인 ]  ── 현재 상태(등급) 계산
    │
    ├─ 침수: RiskStore 에 상태 보관 ──▶ EventSync(20초 주기)가 읽어 이벤트화
    │
    └─ 인파·노면: 분석 직후 직접 이벤트 기록
       (주기가 길어 중간 상태를 보관할 저장소가 없음)
    │
    ▼
 [ events 테이블 ] ── 같은 지점의 열린 이벤트가 있으면 갱신(중복 억제)
    │                 등급이 내려가도 peak_level 은 보존
    ▼
 [ 관제요원 ] 확인 → 조치 → 종결   (event_actions 에 이력)
    │
    ├──▶ 알림 요청 (notifications)  ── 주민 경보는 2인 승인
    └──▶ 시설물 제어 (facility_controls) ── 기본은 「권고만」
```

### 6-2. 중복 억제와 `peak_level`

같은 지점에서 위험이 이어질 때 **이벤트를 새로 만들지 않고 갱신**합니다.
그렇지 않으면 관제요원의 목록이 같은 사건으로 도배됩니다.

`peak_level` 을 따로 두는 이유는, 위험이 지나가 등급이 내려가도 **그 사건이
얼마나 심각했는지**가 남아야 사후 분석과 보고가 가능하기 때문입니다.

### 6-3. 개인정보 마스킹 흐름

```
 프레임 / 제보 사진
    │
    ▼
 core/image_mask.py  ── YOLO 로 person 검출 → 강한 픽셀화(1/18 축소 후 확대)
    │
    ├─ 성공 ──▶ 저장·표시
    └─ 실패(모델 없음 등) ──▶ **표시하지 않음** + 상태를 화면에 알림
```

**흐림이 아니라 픽셀화를 쓴 이유** — 흐림은 복원 가능성이 남습니다.

**실패 시 원본을 그냥 내보내지 않습니다.** 가리지 못한 사실을 상태로 남겨
담당자가 판단하게 합니다.

### 7-1. 프런트엔드에 프레임워크를 쓰지 않은 이유

React·Vue를 쓰면 빌드 산출물과 노드 의존성이 따라옵니다. 망분리 환경에서
**패키지를 받을 수 없고**, 지자체 인수인계 시 빌드 체인까지 넘겨야 합니다.
화면 복잡도가 이를 정당화할 수준이 아니라고 판단했습니다.

## 8. 배포 구조

### 8-1. 현재 (개발·시범)

```
 단일 서버
   ├─ uvicorn (127.0.0.1:8000)   ← 워커 1개
   ├─ PostgreSQL 17.7 (포트 5433, 로컬 .tools/pgsql)
   └─ 모델 파일 (models/*.pt)
```

기동·종료는 `run.ps1` / `stop.ps1` 로 감쌌습니다.

### 8-2. 운영 권고 (미적용)

```
 [리버스 프록시 nginx]  ── HTTPS 종단, 정적파일 서빙
        │
        ▼
 [uvicorn — 워커 1]     ← 분석 스레드 중복을 피하려면 1개 유지
        │
        ▼
 [PostgreSQL — 별도 호스트]  ── 정기 백업, 계정 분리
```

**운영 전 반드시 처리해야 할 것**

| # | 항목 | 현재 상태 |
|---|---|---|
| 1 | HTTPS 적용 | ❌ HTTP. 세션 쿠키가 평문으로 오감 |
| 2 | `URBANGUARD_SECRET_KEY` 고정 | ⚠️ `.env` 에 있으나 운영 키 재발급 필요 |
| 3 | DB 계정 분리(앱/관리) | ❌ 단일 계정 |
| 4 | 정기 백업 자동화 | ❌ 수동 |
| 5 | 로그 파일 수집 | ⚠️ `print()` 잔존 (9-2절) |

## 9. 품질 · 운영성

### 9-1. 시험

| 구분 | 수량 | 비고 |
|---|---|---|
| 자동 테스트 | **285건 전부 통과** | 33개 파일 |
| 실서버 검증 | 항목별 수행 | 시험 결과서 참조 |

### 9-2. ⚠️ 로깅이 통일돼 있지 않습니다

`core` 와 신규 `service` 모듈은 `logging` 을 쓰지만, **일부 모듈에 `print()`
가 남아 있습니다.** 운영에서 로그를 파일로 모으거나 수준별로 거르려면
전환이 필요합니다.

### 9-3. 상태 확인

`GET /api/health` 가 다음을 돌려줍니다 — 인증 없이 접근 가능합니다.

- 상시 탐지 대상 수와 도메인별 동작 여부
- 인파 데이터 소스가 실검출인지 모의(mock)인지
- 물 세그멘테이션 백엔드

> **화면만 봐서는 모의 데이터인지 실제 분석인지 구분되지 않습니다.**
> 둘의 신뢰도가 완전히 다르므로 상태로 노출합니다.

## 10. ⚠️ 정직하게 남기는 아키텍처 한계

| # | 한계 | 영향 | 대응 방향 |
|---|---|---|---|
| 1 | **단일 프로세스·단일 서버** | 장애 시 전체 중단 | 이중화는 분석 워커 분리가 선행돼야 함 |
| 2 | **인파 검출이 모의(mock) 상태** | 현재 인원·위험행동 수치는 실제 영상값이 아님 | 실검출 전환 후 현장 캘리브레이션 |
| 3 | **노면 모델이 부산 CCTV에서 탐지 0건** | 도메인 갭(학습 데이터와 촬영 조건 차이) | 자체 CCTV 데이터 라벨링이 필수 경로 |
| 4 | 설정 파일 폴백 이중화 | DB와 파일 값이 갈릴 수 있음 | 시범운영 후 폴백 제거 |
| 5 | 상시 탐지 변경에 재시작 필요 | 관제 중 재시작 부담 | 지점별 워커 개별 기동 구조 |
| 6 | 외부 연계 규격 미확보 | S-70 착수 불가 | 발주처에 규격 요청 필요 |
| 7 | Ultralytics AGPL-3.0 | 납품 시 라이선스 쟁점 | 대체 모델 검토 결론 필요 |
| 8 | **한 카메라에 여러 도메인 상시 지정 시 스트림 경합** | 분석이 거부될 수 있음 | 재시도로 완화. 근본은 상시 지정 축소 또는 프레임 공유 |
| 9 | **노면 결과가 메모리 저장** | 재시작 시 「미분석」로 | 이력이 필요하면 이벤트를 봄. 영속화는 미착수 |
