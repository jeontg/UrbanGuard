## 0. 결론 요약

- **기술적 대안은 명확함 — RF-DETR(Roboflow) 권고.** 탐지·세그멘테이션을 모두 지원하고, **세그멘테이션 모델은 전 크기(Nano~2XL)가 Apache 2.0**. COCO 기준 성능도 YOLO11보다 높다고 보고됨
- **그러나 즉시 전환은 불가능함.** 현재 쓰는 물 세그멘테이션 모델(`models/best.pt`)은 **자체 학습 모델인데 학습 데이터가 저장소·문서 어디에도 없습니다.** 데이터를 찾지 못하면 어떤 프레임워크로도 재학습이 불가능하며, 이것이 전환의 최대 걸림돌입니다
- **작업 범위는 파일 8개 + 어댑터 계층 신설.** 현재 코드가 Ultralytics 고유 API에 19개 라인에서 직접 결합돼 있어, 로더 한 개만 교체하는 방식으로는 해결되지 않습니다
- **용어 주의**: 이것은 라이선스 "회피"가 아니라 **허용적 라이선스 제품으로의 정당한 교체**입니다. AGPL 코드를 쓰면서 의무만 피하는 것은 불가능하며, 그런 접근은 권하지 않습니다

## 1. 후보 비교

| 모델 | 라이선스 | 세그멘테이션 | COCO 성능(보고값) | 비고 |
|---|---|---|---|---|
| **RF-DETR** (Roboflow) | **Apache 2.0** (Nano~Large 탐지 + **세그 전 크기**) | ✅ **지원** (RF-DETR-Seg) | RF-DETR-L 56.5 AP, T4에서 6.8ms | ICLR 2026. 탐지 XL/2XL만 PML 1.0 |
| D-FINE (USTC) | Apache 2.0 | 🔶 별도 파생(D-FINE-seg) | D-FINE-L 54.0 AP / 8.07ms, X 55.8 AP | 본체는 탐지 전용 |
| RT-DETR / v2 (Baidu) | Apache 2.0 | ❌ 탐지 전용 | RT-DETRv2 54.3 AP | 검증 이력 풍부 |
| YOLOX (Megvii) | Apache 2.0 | ❌ 탐지 전용 | 상대적으로 구세대 | 안정적이나 성능 열위 |
| **현재: Ultralytics YOLO11** | **AGPL-3.0** | ✅ 지원 | YOLO11x 50.9 AP | 상용 시 Enterprise 라이선스 필요 |

**RF-DETR을 권고하는 이유**: 이 프로젝트는 **탐지(사람·차량·노면손상)와 세그멘테이션(물 영역)을 모두** 사용합니다. 후보 중 두 작업을 하나의 Apache 2.0 스택으로 덮는 것은 RF-DETR뿐입니다. D-FINE/RT-DETR/YOLOX를 쓰면 세그멘테이션용 프레임워크를 따로 도입해야 해 유지보수 대상이 둘로 늘어납니다.

**⚠️ 성능 수치 해석 주의**: 위 AP 값은 전부 **COCO 벤치마크** 기준입니다. 우리 실제 과제(부산 CCTV의 흙탕물 영역 세그멘테이션)와는 데이터 성격이 달라 **그대로 이전되지 않습니다.** Phase 2 도로손상 검증에서 이미 겪었듯, 벤치마크 성능과 현장 성능은 별개입니다. 실제 성능은 우리 데이터로 재학습해 직접 측정해야 알 수 있습니다.

### 사전 검증 — 기존 `best.pt`는 지금도 정상 동작하는가?

**① 맑은 날 부산 CCTV 14장 (오탐 검사)** — 결과: **양호**

| 결과 | 건수 |
|---|---|
| 물 미검출(정상) | 13 / 14 |
| 미미한 오탐 | 1건 (BLOCK-OLYMPIC, 화면의 0.43%, conf 0.155) |

→ 비가 안 오는 날 물을 잘못 잡아내지 않습니다. **라이브 대시보드의 침수 판정은 신뢰할 만합니다.**

**② 로컬 침수 영상(`data/samples/flood/underpath_flood1.mp4`) — 결과: 🚨 사실상 미동작**

- 26프레임 전부에서 화면의 약 19%를 물로 검출(conf 0.18~0.20)
- 그런데 **마스크가 실제 침수 구간이 아니라 좌우 검은 여백(레터박스)에 찍혔습니다.** 정작 물이 찬 지하차도 노면은 전혀 잡지 못함
- 이 영상은 1920×1080으로 좌우에 검은 세로 띠가 있는 레터박스 영상입니다
- **후속 검증(레터박스 제거 후 재시험): 검출 0건.** 화면 가득 물이 차 있고 차량이 물살을 가르며 지나가는 장면인데도 전혀 검출하지 못했습니다
- → 즉 "19% 검출"은 실제 물이 아닌 **검은 여백에서 나온 허위 신호**였고, **이 모델은 해당 침수 영상에서 사실상 동작하지 않습니다.** (⚠️ 단, 영상 1건·야간 저조도라는 어려운 조건 기준이므로 다른 침수 영상으로 추가 검증 권장)

### 🐛 이 검증에서 새로 발견한 버그 (라이선스와 무관, 별도 조치 필요)

**레터박스/필러박스가 있는 영상을 입력하면 검은 여백을 물로 오인합니다.**

- 영향 범위: 라이브 CCTV 경로는 레터박스가 없어 **영향 없음**. 다만 `tot-flood-standalone --video`로 임의 영상을 분석하는 경로는 **오탐 발생**
- 권고 조치: 전처리 단계에서 레터박스 검출·제거(crop)를 추가하거나, 유효 영역 마스크를 적용
- 이는 프레임워크를 바꾸든 안 바꾸든 고쳐야 할 사안입니다

### ⚠️ 방안 A(의사라벨 증류)의 법적 함정

→ **방안 A는 법무 확인 전에는 채택하지 마시기 바랍니다.** 채택하더라도 반드시 사전 자문을 받아야 합니다.

### 📌 사용자 결정: 방안 B 채택 (2026-07-31)

Enterprise 라이선스 검토와 별개로 **방안 B(자체 라벨링 후 재학습)로 진행**하기로 결정했습니다.
위 ②의 후속 검증에서 **기존 모델이 실제 침수 영상에서 동작하지 않음**이 드러나, 아래 "Enterprise 재검토" 논거의 전제("이미 잘 동작하는 모델")가 약해진 점도 이 결정을 뒷받침합니다.

→ 구체적 작업 절차·도구는 **`docs/flood_water_dataset_workflow.md`** 참고 (도구 4종 제작·검증 완료)

### 💡 (참고) Enterprise 라이선스 재검토 논거 — 전제 일부 무효화됨

데이터 회수가 불가능해지면서 **비용 구조가 역전됐습니다.**

- 전환 시 필요 작업: 침수 라벨링 데이터 신규 구축(호우 이벤트 대기 + 라벨링) + RF-DETR 재학습 + mAP50 0.864 이상 달성 검증 + 코드 8개 파일 개편 + 트래커 교체
- Enterprise 구매 시: **위 작업 전부 불필요.** `best.pt`를 그대로 쓰고 코드도 그대로 유지

즉 "성능 좋은 대체 모델을 찾는 것"보다 **"이미 잘 동작하는 모델을 합법적으로 계속 쓰는 것"**이 더 합리적일 수 있는 상황입니다. Ultralytics Enterprise 라이선스 견적을 받아 위 전환 비용(인건비 + 일정 지연)과 정량 비교해 보시길 권합니다.

**⚠️ 확인 필요**: Ultralytics Enterprise 라이선스의 실제 가격은 공개되어 있지 않아 이번 조사로 확인하지 못했습니다. 영업 문의(ultralytics.com/license)로 견적을 받아야 비교가 가능합니다.

## 3. 전환 작업 범위

### 수정 대상 (소스 8개 + 테스트 1개)

| 파일 | 결합 내용 |
|---|---|
| `common/models_loader.py:38,43` | 공식 로더 — `YOLO()`, `.to()`, `model.names` |
| `service/runner.py:194-195` | **로더 우회** — 서비스 런타임이 `YOLO()` 직접 호출 |
| `traffic_weather/perception/detection_source.py:136,144,149,175,178-184` | **로더 우회** + `res.boxes`/`b.cls`/`b.xyxy`/`b.conf` 직접 순회 |
| `flood/water_segmentation.py:60-66,81-92` | `masks.xy` 폴리곤, `result.boxes.conf` |
| `flood/object_detection.py:95,101,106,111-115` | `model.track()` — **BoT-SORT 내장 트래커 의존** |
| `road/defect_detection.py:66,74-79` | `model.predict()`, `b.xyxy/cls/conf` |
| `flood/standalone_pipeline.py:261` | `model.predictor = None` — ultralytics 내부 속성 직접 조작 |
| `scripts/train_road_defect_prototype.py`, `_v2.py` | 학습 스크립트 |

### 구조적 문제

`models_loader.py`는 **로드만 감싸는 얇은 래퍼**이고 추론 인터페이스는 감싸지 않습니다. 그 결과:
- Ultralytics Results 고유 API를 직접 쓰는 코드가 **19개 라인 / 4개 파일**
- 로더를 우회해 `YOLO()`를 직접 호출하는 곳이 **2곳**

→ **로더 한 개 교체로는 불가능**하며, 프레임워크 중립 DTO(`Detection`/`WaterResult` 등)로 감싸는 **어댑터 계층 신설이 선행**돼야 합니다.

### 추가 고려사항 — 객체 추적(트래킹)

`flood/object_detection.py`가 Ultralytics 내장 `model.track()`(BoT-SORT)을 씁니다. RF-DETR에는 트래커가 내장돼 있지 않으므로, **별도 트래커(예: ByteTrack, BoT-SORT 독립 구현) 도입이 추가로 필요**합니다. 이 부분의 라이선스도 함께 확인해야 합니다.

1. ~~**[선행] `RoS` 계정 PC에서 학습 데이터 회수**~~ → **회수 불가 확정(2026-07-31).** 이에 따라 2-B절의 대안 검토로 대체하며, **Enterprise 라이선스 견적 확보가 최우선 과제**가 되었습니다
2. **[선행] 법무 검토** — ①Enterprise 라이선스 비용 ②RF-DETR 전환 비용(재학습+개발) 비교. AGPL 준수(전체 소스 공개)가 공공납품 계약상 가능한지도 함께 확인
3. **어댑터 계층 신설** — 프레임워크 교체와 무관하게 **지금 해도 이득인 리팩터**(현재 결합도가 과함). 전환을 결정하지 않아도 선행 가능
4. **RF-DETR PoC** — 노면손상(`road/`)처럼 이미 재학습 데이터가 있고 아직 mock인 모듈부터 시험 적용해 위험 없이 검증
5. **물 세그멘테이션 재학습·검증** — 기존 `best.pt`와 동일 입력에서 성능 비교(회귀 테스트)
6. **전면 전환** 또는 **Enterprise 라이선스 구매** 최종 결정

**4번을 먼저 하는 이유**: 노면손상 모듈은 현재 mock 상태라 망가뜨릴 게 없고, RDD2022 학습 데이터도 이미 확보돼 있습니다. 여기서 RF-DETR 학습·추론 파이프라인을 검증한 뒤 침수 모듈에 적용하는 것이 안전합니다.
