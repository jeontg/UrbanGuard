## 0. 결론 먼저

○ **직전 회차 갭 분석에서 「매일 쓰는데 없는 기능」으로 지목한 3종을 모두

○ **⚠️ 디지털 SOP 의 기본 12단계는 어느 기관의 행동매뉴얼도 아닙니다.**

  「기본안 12/12단계」로 그 사실을 드러냅니다. 도입 기관 매뉴얼로 교체 필요

## 1. ① 영상 반출 관리대장 (S-94)

### 1-1. 무엇을 하는가

관제 영상을 외부에 제공한 내역을 기록합니다. 영상을 밖으로 내주는 순간
개인정보를 제3자에게 제공한 것이 되고, 그 사실은 대장으로 남겨야 합니다.

| 항목 | 내용 |
|---|---|
| 근거 법령 | 개인정보 보호법, 「지방자치단체 영상정보처리기기 통합관제센터 구축 및 운영 규정」 |
| 화면 | `/admin/disclosure` (관리자 묶음) |
| 테이블 | `video_disclosures` (22컬럼) |
| 마이그레이션 | `c3f81d24e9a7` |
| 권한 | SYS 전체 · MGR 등록·정정 · OPR 열람만 |

> ⚠️ 법령·규정명은 일반적으로 통용되는 명칭으로 적었습니다. **조문 번호는
> 넣지 않았습니다** — 기관마다 인용 방식이 달라, 틀린 조문이 기본값으로
> 박히면 대장 전체가 틀린 근거로 채워집니다. 근거 입력란은 자유 입력이며
> 자주 쓰는 유형 6종만 선택지로 제공합니다.

### 1-2. 기록 항목

| 구분 | 항목 |
|---|---|
| 요청 | 요청 일시 · 요청 기관 · 요청자 · 연락처 · **반출 근거** · 이용 목적 |
| 대상 | 대상 지점(CCTV) · 촬영 기간(시작~종료) |
| 처리 | 반출 형태(열람/사본/원본) · 제3자 비식별 여부 · 처리 일시 · 처리자 |
| 파기 | 파기 예정일 · 파기 완료일 |
| 정정 | 원본 참조 · 정정 사유 |

### 1-3. 설계 판단 4가지

**가. 근거 없이는 저장되지 않습니다**
- 근거를 적을 수 없는 반출은 애초에 하면 안 되는 반출입니다
- 코어 모듈(`core/video_disclosure.py`)에서 막습니다

**나. 삭제 라우트를 만들지 않았습니다**
- 화면에도 삭제 버튼이 없고, 시험이 「삭제 라우트가 없음」을 못박습니다
- 잘못 적었으면 **정정 사유를 남기고 새 줄**을 만듭니다. 원본은 「정정됨」으로
  흐리게 남고, 정정본이 원본을 가리킵니다

**다. 파기 지연을 요약 맨 앞에 뒀습니다**
- 종이 대장에서 **가장 자주 비는 칸**이 파기 여부입니다
- 파기 예정일이 지났는데 파기 기록이 없으면 「기한 초과」로 붉게 표시
- 사본·원본 제공은 기본 30일 후 파기 예정으로 자동 설정(화면에서 변경 가능).
  **열람만 한 건은 남는 사본이 없어 파기 대상이 아닙니다**

**라. 카메라에 외래키를 걸지 않았습니다**
- CCTV가 나중에 삭제돼도 대장은 남아야 합니다. 지점 ID 문자열만 저장하고
  이름은 조회 시 붙입니다

### 1-4. 개인정보 취급 유의

- **요청자 성명·연락처가 개인정보입니다.** 화면에 「캡처를 외부로 보내지
  마십시오」를 명시했습니다
- 보존기간이 지나면 대장 자체도 파기 대상입니다. **파기 시점은 기관 규정을
  따르며, 제품이 자동 삭제하지 않습니다** — 감사 자료를 시스템이 임의로
  지우면 안 되기 때문입니다

## 2. ② 디지털 SOP (S-86)

### 2-1. 무엇을 하는가

이벤트 등급이 올랐을 때 무엇을 순서대로 해야 하는지를 화면이 말해 줍니다.

지금까지 화면은 「경계입니다」까지만 말하고, 그다음은 근무자의 기억과 벽에
붙은 코팅지에 맡겨져 있었습니다. **야간에 혼자 근무하는 상황실에서 그 둘은
믿을 것이 못 됩니다.**

| 항목 | 내용 |
|---|---|
| 화면 | `/settings/sop` (편집) · `/events/{id}` (이행 체크) |
| 테이블 | `sop_steps` · `event_sop_checks` |
| 마이그레이션 | `d5a2b70c14e8` |
| 권한 | 편집 SYS·MGR / 이행 체크는 **EVENT/EDIT** (관제요원 가능) |

### 2-2. 권한을 나눈 이유

- **편집은 SOP 자원**, **이행 체크는 EVENT 자원**으로 판정합니다
- SOP 를 따르는 것은 이벤트 처리 행위이고, 그 권한은 관제요원에게 이미
  있습니다. SOP/EDIT 로 잠그면 **정작 절차를 수행하는 사람이 체크를 못 합니다**
- SOP 를 도메인 종속으로 두지 않았습니다 — 도메인 무관 공통 단계가 있어,
  MGR 담당 도메인으로 자르면 공통 단계를 아무도 못 고칩니다

### 2-3. ⚠️ 기본 12단계의 성격 (중요)

**제품이 심어 둔 단계는 어느 기관의 행동매뉴얼도 아닙니다.**

- 지자체마다 통제 기준·통보 계통·전담 부서가 달라 제품이 정할 수 없습니다
- 내용은 **이 시스템이 실제로 할 수 있는 행위**(부서 통보·기관 통보·시설물
  제어 요청·조치 기록·종결)에서만 뽑았습니다
- 화면이 「**기본안 12/12단계**」를 상단에 붉게 띄웁니다. 숫자로 보여 주지
  않으면 아무도 바꾸지 않은 채 납품됩니다
- 한 번이라도 고치면 그 단계는 「기관 작성」으로 바뀝니다
- 재기동해도 **고쳐 둔 내용을 덮어쓰지 않습니다**. 지운 단계도 되살리지
  않습니다(지운 것은 의도입니다)

기본 단계 구성 — 공통 2 · 주의 1 · 경계 1 · 심각 2 · 침수 2 · 인파 2 · 노면 2

### 2-4. 설계 판단 3가지

**가. 등급은 정확히 일치할 때만 뜹니다**
- 「경계」 이벤트에 「주의」 단계까지 붙이면 체크리스트가 길어져 아무도 안
  읽습니다
- 등급이 오르면 상위 단계가 새로 뜨고, 이미 찍은 기록은 그대로 남습니다

**나. 막지 않고 경고합니다**
- 필수 단계가 다 안 찍혀도 **종결을 막지 않습니다**
- 현장에는 규정대로 못 하는 상황이 실제로 있고, 막으면 사람은 아무 칸이나
  찍고 넘어갑니다
- 대신 종결 시 확인창이 뜨고, 「SOP 0/6 (필수 3건 미이행)」이 조치 이력에
  박힙니다. 종결하면 등급이 고정돼 나중에 다시 계산할 수 없기 때문입니다

**다. 「해당 없음」은 사유가 있어야 합니다**
- 사유 없이 넘길 수 있으면 체크리스트가 한 번에 다 넘어가고, 그러면 아무
  의미가 없습니다

**라. 단계를 지워도 이행 기록은 남습니다**
- 단계 참조만 끊기고 제목은 기록에 복사돼 있습니다. 「무엇을 했는지」가
  사라지면 안 됩니다

## 3. ③ 교대 인수인계 (S-04)

### 3-1. 무엇을 하는가

근무조가 바뀔 때 넘길 내용을 적습니다. **관제는 24시간 이어지는데 사람은
8~12시간마다 바뀝니다.** 그 이음매에 아무것도 없으면, 야간에 열려 있던
이벤트가 주간 근무자에게 전달되지 않은 채 아무도 안 보게 됩니다.

| 항목 | 내용 |
|---|---|
| 화면 | `/handover` (이벤트 묶음) |
| 테이블 | `shift_handovers` |
| 마이그레이션 | `e7b3c9014f2a` |
| 권한 | SYS·MGR·OPR 모두 작성·인수 확인 가능 |

### 3-2. 미처리 이벤트 자동 첨부

**손으로 옮겨 적으면 반드시 빠집니다.** 빠지는 것은 대체로 「별일 아니라고
생각한 것」이고, 사고는 거기서 납니다.

- 작성 시점과 **인계 시점**에 열려 있는 이벤트를 자동으로 담습니다
- 이벤트마다 **SOP 이행 현황(3/6, 필수 2건 남음)**을 함께 담습니다 —
  인수자가 이벤트를 하나씩 눌러 보지 않고 「무엇이 남았는지」를 알아야 합니다
- 제출 전 미리보기로 「지금 넘어갈 미처리 이벤트 n건」을 보여 줍니다

### 3-3. 스냅샷으로 굳히는 이유

지금 열린 이벤트를 그때그때 조회하지 않고 **인계 시점 목록을 그대로 저장**
합니다.

나중에 이벤트가 종결돼도 「**인계 시점에 무엇이 열려 있었는가**」가 남아야
하기 때문입니다. 사후 검토는 그 시점의 사실을 묻지, 지금의 사실을 묻지
않습니다.

### 3-4. 설계 판단 3가지

**가. 넘긴 뒤에는 고칠 수 없습니다**
- 내용이 나중에 바뀌면 인수자가 확인한 것이 무엇인지 알 수 없습니다
- 덧붙일 내용은 인수 확인 메모에 적습니다

**나. 인계자 본인은 인수 확인할 수 없습니다**
- 혼자 넘기고 혼자 받으면 인수인계가 아닙니다
- 확인 대기 목록에서도 내가 넘긴 것은 빠집니다

**다. 실제로 받은 사람으로 인수자를 덮어씁니다**
- 미리 적어 둔 인수자 이름이 있어도, 확인한 계정으로 바꿉니다
- 근무 교대는 계획대로 안 되는 일이 흔합니다

### 3-5. 근무조 편성은 고정하지 않았습니다

2교대·3교대·4조3교대와 명칭이 기관마다 달라, 목록으로 고정하지 않고
자유 입력 + 예시 5종(주간·야간·심야·오전·오후) 제안 방식으로 두었습니다.

## 4. 권한 매트릭스 변경

기존 16자원 → **19자원**으로 늘었습니다.

| 자원 | SYS | MGR | OPR | 비고 |
|---|---|---|---|---|
| `video_disclosure` (S-94) | 전체 | 열람·등록 | 열람 | 반출 요청이 오는 곳이 부서 |
| `sop` (S-86) | 전체 | 열람·편집 | 열람 | 기관 매뉴얼을 아는 사람이 부서담당자 |
| `handover` (S-04) | 전체 | 열람·작성·확인 | **열람·작성·확인** | **OPR 에 APPROVE 를 주는 유일한 자원** |

> `handover` 는 관제요원이 주체인 유일한 자원입니다. 교대는 상황실
> 근무자끼리 하는 일이라, 부서담당자에게만 인수 확인 권한을 주면 밤에 넘긴
> 인계문을 아침에 아무도 확인하지 못합니다.

세 자원 모두 **도메인 종속이 아닙니다** — 관제요원은 도메인별로 근무하지
않습니다.

## 5. 감사 로그 연동

세 기능 모두 **행위 자체를 감사 로그(S-91)에도 남깁니다.**

| 행위 코드 | 표시명 |
|---|---|
| `disclosure.create` / `.correct` / `.dispose` | 영상 반출 등록 / 정정 / 파기 확인 |
| `sop.save` / `.delete` / `.seed` | SOP 단계 등록·수정 / 삭제 / 기본안 채우기 |
| `handover.submit` / `.ack` | 교대 인계 / 교대 인수 확인 |

대장·인계문 자체가 기록이지만, **그것을 누가 만졌는지**는 감사 로그가
답합니다 — 대장의 「등록자」가 진짜 등록한 사람인지는 대장 자신이 모릅니다.
