## 0. 결론 먼저

○ **침수 모델이 블록마다 새로 만들어지고 있었습니다.** 같은 가중치가 지점
  수만큼 메모리에 올라갔습니다. **이제 하나만 만듭니다**

○ **어느 런타임을 쓰든 이득입니다.** OpenVINO 를 안 켜도 이득이고, 켜면
  이득이 커집니다(지점당 26.7초)

○ ⚠️ **「분석기 공유」와 혼동하면 안 됩니다.** 분석기는 추적 ID·배회 타이머를
  들고 있어 **공유하면 지점 간에 뒤섞입니다.** 여기서 공유하는 것은
  **가중치뿐**입니다

○ ⚠️ **앞서 「39지점 × 27초」라고 말한 것을 정정합니다** — 상시 탐지는
  **7지점**이고 모델 인스턴스는 **5개 안팎**입니다

## 1. ⚠️ 먼저 정정 — 39지점이 아닙니다

앞선 보고에서 「39지점이 각각 27초씩 예열하면 기동이 끝나지 않는다」고
적었습니다. **확인하지 않고 한 말이었습니다.**

### 실제 상시 탐지 지점

| 도메인 | 상시 지점 | 모델 인스턴스 구조 |
|---|---|---|
| 침수 | **3** | `runner.py` — **블록마다 로드**(캐시 없음) → **3개** |
| 인파 | **1** | `continuous.py` — 카메라마다 분석기 → 1개 |
| 노면 | **3** | `_road_analyzer` **전역 1개**를 3지점이 돌려 씀 → **1개** |
| 마스킹 | — | `image_mask._model` **모듈 전역** → **1개** |

**39는 등록된 전체 CCTV 수**이고, 상시 탐지는 **7지점**입니다.
모델 인스턴스는 **5개 안팎**입니다.

### 그래서 OpenVINO 기동 지연은

| 런타임 | 인스턴스당 | 5개 기준 |
|---|---|---|
| PyTorch (현재) | 2.0초 | 10초 |
| ONNX | 1.5초 | 7.5초 |
| **OpenVINO** | **26.7초** | **약 2분 15초** |

**17분이 아니라 2분입니다.** 과장했습니다.

---

## 2. 무엇을 고쳤나

`_load_water_model()` 이 **블록마다 호출**되고 있었습니다(`runner.py` 의
`_ctx` 구성 루프). 캐시가 없어 매번 새로 만들었습니다.

```
이전 : 블록 3개 → 모델 3벌
이후 : 블록 몇 개든 → 모델 1벌
```

| 런타임 | 지점당 | 3지점 (이전 → 이후) |
|---|---|---|
| PyTorch | 2.0초 | 6.0초 → **2.0초** |
| ONNX | 1.5초 | 4.5초 → **1.5초** |
| OpenVINO | 26.7초 | 80.1초 → **26.7초** |

메모리도 `best.pt` 기준 약 **20MB × 3 → 20MB** 입니다.

### 실패도 기억합니다

안 그러면 블록마다 재시도하며 **같은 오류를 지점 수만큼** 로그에 찍습니다.
정작 봐야 할 다른 로그가 묻힙니다.

---

## 3. 왜 안전한가 — 모델은 무상태다

**가중치는 아무것도 기억하지 않습니다.** 프레임을 받아 결과를 돌려줄 뿐이라
**공유해도 결과가 달라지지 않습니다.**

지점별 상태는 전부 분석기 쪽에 있습니다.

```
분석기 (지점마다)  ─┐
  · ROI             │
  · 추적 ID         ├─→  모델 (하나) ─ 무상태
  · 배회 타이머      │
  · surge 기준선    ─┘
```

---

## 4. ⚠️ 분석기는 공유하면 안 됩니다

코드에 이렇게 적혀 있습니다.

> 카메라마다 별도 분석기를 둔다. **하나를 공유하면 추적 ID 와 배회 타이머가
> 지점 간에 뒤섞인다.**

공유하면 **A지점 사람이 B지점에서 「계속 배회 중」으로 잡힙니다.**
**성능이 아니라 정확성 문제**입니다.

> 누군가 나중에 공유 범위를 넓히면 걸리도록 **시험으로 묶어 뒀습니다.**

---

## 5. 왜 이건 런타임 결정 없이 해도 되나

| 결정 | 이 작업의 값어치 |
|---|---|
| **현행 유지** | 기동 4초 단축 + 메모리 40MB 절약 |
| **ONNX 채택** | 기동 3초 단축 |
| **OpenVINO 채택** | **기동 53초 단축** — 선행 조건이 됨 |
| 납품 서버가 AMD | OpenVINO 는 무의미해지지만 **이 개선은 남음** |

**어느 쪽으로 가도 손해가 없습니다.** 그래서 결정 전에 먼저 했습니다.

---

## 6. 아직 결정이 필요한 것

| # | 항목 | 왜 결정이 먼저인가 |
|---|---|---|
| 1 | **납품 서버 CPU 제조사** | AMD 면 OpenVINO 이점이 사라짐 |
| 2 | OpenVINO 채택 여부 | 예열 전략·기동 지연 대응의 필요성이 갈림 |
| 3 | 기동 2분을 감수할지 | 대안: **백그라운드 예열 후 갈아 끼우기** |

> 3번은 인스턴스 공유가 유일한 해법이 아닙니다. **예열을 백그라운드로 돌리고
> 준비되는 대로 교체**하면 기동을 막지 않습니다. 다만 그동안은 느린 모델로
> 도는 셈이라, **어느 쪽이 나은지는 운영 조건을 봐야** 합니다.
