## 0. 결론 먼저

○ **화면에서 고른 모델이 이제 실제로 쓰입니다.** 지금까지 침수·인파는
  **설정은 저장되는데 읽는 코드가 없었습니다.** 「바뀐 줄 알고 관제하는」
  상태라 가장 나쁜 결함이었습니다

○ **⚠️ 인파 계수(밀집도)는 여전히 안 바뀝니다.** 구조가 달라서입니다.
  숨기지 않고 화면이 그대로 말하게 했습니다

○ **YOLO26을 받아 재 봤습니다. 지금 갈아탈 근거가 없습니다.**
  26n은 사람을 **1/3만** 찾고, 26s는 **속도 이득이 없습니다**(0.94배)

○ 후보 모델(ONNX·OpenVINO·YOLO26)이 목록에 뜨고, 고르면
  **task·장치·예열이 자동 처리**됩니다

## 1. 도메인별 실제 상태 — 이 표가 핵심입니다

| 도메인 | 고른 모델이 실제로 쓰이나 | 반영 시점 |
|---|---|---|
| **노면** | ✅ 된다 | 재기동 없이 **다음 순회부터** |
| **침수** | ✅ 된다 **(이번에 배선)** | **재기동 후** |
| **인파 — 개인정보 마스킹** | ✅ 된다 **(이번에 배선)** | **다음 마스킹부터** |
| **인파 — 계수(밀집도)** | ❌ **안 된다** | 구조가 다름 |

### 침수가 왜 안 됐나

`configs/water_config.yaml` **만** 보고 설정을 무시했습니다. 화면은
「재기동하면 반영됩니다」라고 안내했지만 **재기동해도 바뀌지 않았습니다.**

`_flood_model_rel()` 을 두어 **설정이 우선**하도록 했습니다.

### 인파 계수는 왜 안 되나

인파 계수는 **torchvision FasterRCNN 을 아키텍처 이름으로** 로드합니다.
레지스트리는 **파일 경로**로 모델을 고르는 구조라 애초에 맞지 않습니다.
단순 배선으로 될 일이 아니라 **분석기 재설계**가 필요합니다.

대신 레지스트리의 `crowd` 항목이 실제로 가리키던 소비처인
**개인정보 마스킹**(`core/image_mask.py`)을 배선했습니다.

> **이 차이를 화면이 그대로 말합니다.**
> 「마스킹에는 다음 마스킹부터 바로 반영됩니다. ⚠ 다만 **인파 계수(밀집도)는
> 바뀌지 않습니다**」 — 이 문구가 사라지지 않도록 시험으로 묶었습니다.

## 2. 안전장치 — 고른 모델을 못 쓸 때

도메인 성격에 맞춰 다르게 정했습니다.

| 상황 | 처리 | 왜 |
|---|---|---|
| 마스킹 모델 파일 없음 | **기본값으로 되돌림** | 마스킹이 멈추면 **개인정보가 가려지지 않은 채 저장**될 수 있다 |
| 침수 모델 파일 없음 | 설정파일 값으로 되돌림 | 고를 수 없게 되는 것보다 예전 모델로 도는 편이 낫다 |
| 설정 조회 실패(DB 정지 등) | 기본값으로 뜬다 | **DB 가 없어도 파이프라인은 떠야 한다** |
| 모델 교체 후 | 마스킹 **캐시를 비운다** | 안 비우면 프로세스가 사는 동안 예전 모델이 계속 쓰인다 |

## 3. 후보 등록 — 목록에서 보여야 고른다

| 항목 | 처리 |
|---|---|
| 위치 | `models/candidates/` |
| 인식 | `.onnx` · `*_openvino_model` 폴더 · **`.pt`** |
| 표시 | 「… — ONNX Runtime」처럼 런타임을 드러냄 |
| 설명 | **「운영에 적용되어 있지 않습니다」** |
| `in_use` | 비움 — 운영 표시를 달지 않음 |
| 기본 선택 | **후보로 바뀌지 않음** |

> ⚠️ **고쳐야 했던 것** — 기존 규칙이 `best.pt` · `last.pt` 만 받아서
> `models/candidates/yolo26n.pt` 가 **목록에서 통째로 숨었습니다.**
> 받아 놓고 안 보이면 비교할 방법이 없습니다.

## 4. YOLO26 실측 — 광복로 실제 인파 영상 12프레임

| 모델 | 장당 | 배수 | 검출 인원(합계) |
|---|---|---|---|
| **YOLO11s (운영)** | 310.9ms | 1.00 | **135명** |
| **YOLO26n** | **162.6ms** | **1.91배** | **43명** |
| **YOLO26s** | 329.4ms | **0.94배** | 138명 |

### 신뢰도 문턱을 낮춰도 회복되지 않습니다

| conf | YOLO11s | YOLO26n | YOLO26s |
|---|---|---|---|
| 0.25 | 135 | **43** | 138 |
| 0.15 | 259 | **108** | 244 |
| 0.10 | 365 | **188** | 354 |
| 0.05 | 587 | **368** | 592 |
| 0.03 | 794 | **571** | 799 |

**모든 문턱에서 일관되게 적습니다.** 보정 문제가 아니라 검출력 차이입니다.

### 운영 모델과의 일치 (IoU 0.5)

| 후보 | 짝지어진 상자 | 해석 |
|---|---|---|
| YOLO26n | 40개 (운영 135 중 **30%**) | 운영이 찾는 것의 1/3만 찾음 |
| YOLO26s | 88개 (운영 135 중 **65%**) | 운영만 47개 · 26s만 50개 — **절반 가까이 다른 대상** |

### 판단

**지금 갈아탈 근거가 없습니다.**

- **YOLO26n** — 1.91배 빠르지만 사람을 1/3만 찾습니다. 밀집도가 핵심 지표인
  인파 관제에서 **인원을 놓치면 위험을 과소평가**합니다. 안전 시스템에서
  가장 나쁜 실패 방향입니다
- **YOLO26s** — 속도 이득이 없습니다(0.94배, 오히려 느림)

> ★ **마지막 줄이 가장 중요합니다.** 26s 와 운영 모델은 **개수는 비슷한데
> 절반 가까이 다른 대상**을 잡습니다. **정답 라벨이 없어 어느 쪽이 맞는지
> 판정할 수 없습니다.** 계획 B 1단계(고정 평가셋 구축)가 왜 먼저인지를
> 이 측정이 그대로 보여 줍니다.

## 5. 측정 중 스스로 잡은 오류

첫 실행의 프레임이 `train_batch0.jpg` · `val_batch0_pred.jpg` —
**학습 시각화 모자이크**였습니다. 작은 학습 이미지를 격자로 붙이고 라벨을
덧그린 그림이라 사람 검출 비교로는 아무 의미가 없습니다.

광복로 실제 영상에서 다시 뽑아 재측정했습니다.

> **속도는 어떤 그림으로 재도 되지만, 검출 비교는 실물이어야 합니다.**

## 7. 시험

| 구분 | 결과 |
|---|---|
| 신규 시험 누계 | **23건** |
| 전체 회귀 | **1,018건 통과 · 3건 건너뜀 · 실패 0** |
| 소요 | **274초 (4분 34초)** |

기준선 995건 + 23건 = 1,018 로 맞습니다.

### 시험이 못박은 것

- 침수·마스킹이 **고른 모델을 우선**한다
- 없는 파일을 고르면 **되돌아간다**
- **DB 가 없어도 파이프라인이 뜬다**
- 마스킹 **캐시를 비울 수 있다**
- 화면 안내문이 **「인파 계수는 안 바뀐다」고 말한다**
- 후보 폴더의 `.pt` 가 **목록에 나온다**
- 운영 기본값이 **후보로 바뀌지 않는다**
